### A-6　认领（msku 级）与格子（货号级）的粒度差

**背景**：运营认领 msku，但格子是 `店铺 × 货号 × 月`。
同店铺同货号可能有多个 listing（新旧并存）。

**负责人已说明的业务分水岭**：
```
运营层   msku 级     为具体店铺 listing 准备数量
  ↓ 求和  ← 分水岭
供应链   货号级      同一产品同样生产，不关心店铺
  ↓ 到货
分配回各运营需求      ← 由人做（已由 C4 裁定）
```

| 选项 | 后果 |
|---|---|
| ★ **格子保持货号级；msku 只作销量归属依据 + 可展开明细**（建议） | 新品 / 无 listing 的货号**也能进计划** |
| 格子改成 msku 级 | 粒度统一；★ 但**没有 msku 的货号完全无法进入计划** —— 而新品备货正是最需要提前规划的那类 |

**附带小问**：只认领 msku-001、不认领 msku-002 时，格子的系统预估算谁的销量？
→ 建议：**只算已认领的**，并在格子上显示「由哪几个 msku 撑着」。

**不定的后果**：格子的主键定不下来，整张表设计不出来。

**答：** 格子保持货号级；msku 只作销量归属依据 + 可展开明细

#### D-3　预测算法移植的验收口径　★ 已裁定：**先搬（绿）再修（红），分两步**

**先厘清一件事**：228 门禁证明的**不是「算得准」，是「搬对了」** —— 这是两件事，
不能用同一个测试。

| | 问的是 | 需要什么数据 |
|---|---|---|
| **一致性**（移植验收） | 算法搬过来**行为有没有变** | ★ **任意一组固定输入，越固定越好** |
| **准确性**（模型好不好） | 预测得准不准 | 当前数据 + 跟运营重新对 |

★ 对第一件事来说，「过时」**恰恰是优点**：输入固定不变，
**任何输出差异就只可能来自代码**。换成最新数据，输入天天变，
就永远分不清「输出变了」是搬错了还是数据变了。

**两步走**：

| 步 | 做什么 | 门禁 |
|---|---|---|
| **① 搬（绿）** | 搬 9 个 fixture CSV + 228 格期望值 | ★ 必须**一次绿**。红了就是搬错了，而且能定位到哪一格 |
| **② 修（红）** | 修 `base_rate` 系统性低估约 23% | ★ 门禁**必然变红** —— 那正是「写完先把它弄失败一次」。 红了之后用**当前数据**跟运营对一条新基准 |

★ **顺序不能倒**：先修再搬，就分不清「输出不一样」是搬错了还是修对了。

⚠️ **已知偏差（旧项目至今未修）**：订单是滞后采集的，指数加权把最高权重压在
最不完整的那几天 → `base_rate` 系统性低估约 **23%**。
★ **用完整历史数据做的回测看不见这个偏差** —— 所以第 ② 步不能靠回测验收。

**答：** ★ 先搬（绿）再修（红），分两步

### G-1　`forecast/` 的依赖边界　★ 裁定：**允许 numpy，边界改由测试守**

**我原来的建议是错的。** 我说「只有 `forecast/` 依赖组可含 numpy，`api` 组照旧装不上」——
但新项目**预测是按需的，由 `api` 同步调用**（UC-O4 改格子即重算）。
`api` 进程必须能跑 `forecast`，**所以它必然装得上 numpy**，旧项目那条边界**保不住**。

| 选项 | 后果 |
|---|---|
| ★ **允许，边界改由 layering test 守**（裁定） | 移植能**一次绿**（D-3 优先）；边界靠 `L8` 断言而非「装不上」 |
| 让 `forecast/` 改写成纯标准库 | 保住旧边界；★ 但**违反 D-3 的「一次绿」** —— 改写和移植混在一起，红了分不清是谁的错 |
| `forecast/` 独立成进程，`api` 走 HTTP | 边界最硬；★ 为一个纯函数加一次网络跳转和一套部署，不值 |

★ **旧项目那条边界的原始理由是「读接口零计算」** —— 而新项目的读接口**要算预测**，
前提变了，结论就不该照抄。

⚠️ **附带一个观察**（不在本期做）：预测改成按需窄范围后，量级从
「一轮 105,000 行」降到「几十~几百个 `sku × seller`」，**numpy 未必还有必要**。
可列为 D-3 第②步之后的优化项 —— 但**不许和移植混在一起做**。

### G-2　`repo/` 与 `usecase/` 拆不拆　★ 裁定：**拆**

| 选项 | 后果 |
|---|---|
| ★ **拆**（裁定） | 动作函数里只剩四段式，SQL 全在 `repo/` |
| 合并 | 文件少；★ 但**动作函数会重新长出 SQL** —— 回到 `plan.py` 1871 行那条路 |

合并后 `usecase/place_po.py` 要同时回答「怎么取、怎么判、怎么写、怎么调领星」四个问题。

### H-1　`confirm_token` 怎么生成　★ 裁定：**派生，不存储**

```
confirm_token = sha256(对象类型 + id + 当前内容摘要 + 服务端盐)
```

| 裁定 | 为什么 |
|---|---|
| ★ **不建 token 表、不设过期时间** | 内容一变，摘要就变，token **自然失效** |
| GET 详情时下发 | 人看到的那一版，和他确认的那一版，是同一版 |
| 不匹配 → 409 `stale_confirm_token` | ★ 提示「内容已变，请重新查看」 |

★ **比「存一张 token 表 + 设 5 分钟过期」更准**：
过期时间挡不住「内容在 5 分钟内被别人改了」这种情况，而摘要挡得住。

### H-2　`POST /v1/forecast` 的入参上限　★ 裁定：**500 个 `(sku, seller)`**

超出 → 400 `too_many_targets`，detail 带 `limit` 与 `given`。

★ 依据：一张排货表的行数量级在几十到几百，500 留了余量。
**无上限的后果是一次超大请求把服务拖垮，而且没有任何东西会提前告诉你。**
