## 0. ★★ 先厘清一件事：「人工输入」有两种

这一条是被两个 bug 逼出来的（P15 那个填不出来的货件号输入框就是它）。

| | 生产里是什么 | ★ `mock` 模式下长什么样 | 例 |
|---|---|---|---|
| **① 用户的活** | 人真的要做的判断 | ★ **正常输入框** | 期望销量 · 计划采购量 · 安排发货 · 装箱数据 |
| **② 外部的返回** | ★ 领星 / 亚马逊 / 采集**给我们的** | ★ **必须一眼看出是模拟** | 货件号 · 到货量 · 领星进度 · 实际销量 |

★ **把②画成①，就会得到一个没人填得出来的输入框** —— 而且它看起来像是用户的失职。

### ②怎么表达

```
① 默认由「⏩ 推进一天」自动喂进来 —— 这是主路径，走一遍能看到全链路
② 需要精确控制时，走一个**明确标成「模拟外部」的抽屉**，不混在业务表单里
```

★ 判据：**任何一个字段，如果生产里的值来自外部系统，它就不能长成业务输入框。**

⚠️ 本文所有「原型」一律读作 ★ **前端的 `mock` 模式**（Q-6）——
老原型已冻结，产品前端在 `web/`（`00d` W7）。

## 2. ★★ STA 四步：原型里到底模拟什么

这是外部性最强、也最容易做错的一段（P15 就出在这里）。

| 真实世界 | 我们给什么 | 亚马逊给什么 |
|---|---|---|
| `createInboundPlan` | 货号 · 数量 · 源仓 | `inboundPlanId` |
| `setPackingInformation` | ★ **装箱数据**（人填的，A-8） | — |
| `generatePlacementOptions` | — | ★ **placement 选项，FC 在这里出现** |
| `confirmPlacementOption` | 选中的 option | `taskId` |
| 轮询 `Operate` | `taskId` | ★ **`shipment_id`（可能 N 个）** |

★ **所以原型要模拟的是最后两行**：亚马逊**分几个货件、每个货件收哪些行**。

```
原型里的模拟参数（明确标成「模拟外部」）：
   · 拆成几个货件（默认 1，可调 2~3）
   · 每个货件收哪几行（默认按顺序均分）
```

★ **默认 1 个货件时链路能跑通就够用；但「拆成多个」必须能调出来** ——
否则多货件那条路永远没人走过，而 `test_dispatch_page` 已经吃过一次亏：
**覆盖不到的代码不会失败，所以也不会报警。**

⚠️ **待实调（C 组）**：`confirmPlacementOption` 的返回 / `Operate` 轮询结果里，
**有没有「哪些行进了哪个货件」的逐行明细**？没有的话，行→货件的归属我们自己推不出来。

## 3. 我们系统内要实现的，一共这些

★ 上面所有标 **「我们」** 的加起来：

| 域 | 我们实现的 |
|---|---|
| ② 需求 | 格子 · 提交铸记录 · 销量预估模型 · **库存预测（`14`）** |
| ③ 采购 | 组单（按店铺挑/按货号合并）· 承重墙① · 状态机 |
| ⑤ 排货 | ★ **安排 → 派生排货单**（`15` §2）· 6 项闸 · 承重墙② |
| ⑤ 投送 | 编排多步出站调用 · **断点续跑** · 超时转人工 |
| ⑥ 预测 | 推演 · 落库 · 核对视图（`03` §7） |
| ★ **前端** | ★ **本仓实现**（Q-1）：三个角色的界面 · 网格 · 确认闸展示 · 投送分步回显 |
| 系统 | 网关（幂等 / 审计 / 路径前缀分界）· 每日回执器 · 采集面校验 · ★ `api/ui` 与 `api/pub` 分界 |

★ **我们不实现的**：任何一个 📤📥 —— 那些是调用，不是实现。
把它们写成「我们的功能」，就会出现「我们以为发出去了，其实没有」这类错。
