## 1. 三个阶段

### 阶段 A · 销售计划

| | |
|---|---|
| 界面 | 运营首页（我的计划 · 状态计数 · 筛选排序 · 进度概览）· 计划编辑网格 · 批量添加货号/msku · 版本编辑 |
| 粒度 | ★ 期望销量 = **msku × 月**；计划采购量 = **货号 × 月** |
| 表 | 地基 `actor` + 四张镜像 · `plan` · ★ `plan_demand_cell`（msku×月）· ★ `plan_purchase_cell`（货号×月）· `msku_claim` · `plan_rev` · `plan_line` · `plan_submit_skip` · `plan_line_transition` / `_event` |
| ★ 刷新 | ★ **镜像刷新**（S-33）：`dim/registry.py` 登记表 + `jobs/refresh_dims.py` + APScheduler 进程内日调度 + `dim_refresh_run` 留痕（迁移 `006`）。★ **四张 DIM 镜像不自己刷起来，阶段 A 的外键就永远是手工种的** |
| ★ 预测 | **带**（原理图每格有「销量预估 / 库存预估」）：按需纯函数、★ **不落库**（`08:126`）。系统预估销量 seed 格子；库存预估 = 在仓 − 期望销量（在途货号级不分摊，S-21）。★ **阶段 A 的「系统预估」= 按位置沿用最近 N 个月**（照原型 `rebuildCells` 搬，Task 6 实测）——**是沿用不是预测模型**，铅笔灰只说明「机器给的」，不说明「算得准」；真正的预估模型属后续阶段 |
| 不做 | 排货 · 采购 · 投送 · `03` §7 的预测落库表（留到 B/C 再定） |

★ **原理图里有两个跨阶段的坑**：首页状态计数含「准备排货」「已发货」，
而阶段 A 还没有排货。★ **不许把它们显示成 0** ——「没有」和「还没做」长得一样。
做法：阶段 A 只显示它管得到的态，其余**不渲染**（不是置灰、不是 0）。

**校验判据（全过才进 B）**

```
① 一张计划从建 → 加货品 → 填两种量 → 提交 → 铸出 rev，全程可复现
② ★ 提交时被跳过的格子逐条列出（skipped[]），不静默丢
③ ★ 同一 msku 不能同时归两个「未下单」计划（认领唯一性，库层约束）
④ 计划单记录内容不可变：改了只能出新 rev
⑤ 状态机能画出的退回边真的退得回去
⑥ ★ 前端 mock 与真 API 两种数据源跑出同一屏
⑦ ★ 四张 DIM 镜像能从 CH 刷出来，掉档超阈值拒绝整批且旧镜像不动，每轮在
  dim_refresh_run 里查得到（谁触发 · 多少行进 · 多少行丢 · 为什么丢）
```

**校验判据**

```

⑥ 多仓库采购（单头 wid=0，38%）建得出来
```

## 7. ★★ 三条纪律 —— 杜绝编造非事实要求

```
① ★ 每个数字，要么指到 17/18 的某个 n，要么标「设计取值 · 未实测」
② ★ 每条约束，要么指到 01 的铁律 / 02 的关系 / 00 的裁定，要么不写
③ ★ 指不到出处的 —— 记进 00-待裁定清单，**不许自己定，也不许先写着**
```

★ 为什么第 ③ 条要写死：**「先按合理的写着，以后再改」的东西不会被改** ——
它会被下一个人当成已裁定的事实读走。本项目已经出过三次：
「一个目的地一张」「前端不在本仓」「默认生产 30 天」，
每一次都是先写着、再被外部推翻。

★ 机器核对：`test_doc_index.js` —— §5.2 的表必须覆盖 `docs/` 下每一份文档，
且表里提到的每个文件都必须存在。**少一份就红**。
