> **我们要对接的**（领星 / CH / PM）。

## 0. 约定

| 项 | 约定 |
|---|---|
| 前缀 | ★ 业务路由 `/v1`（`service.toml` 的 `path_prefix = "/v1"`） |
| 健康 | ★ `GET /health` —— **不加前缀**，探活目标 = `base_url + health.path` |
| 鉴权 | `x-internal-key`；★ 未配 → **启动失败**，不是运行时 503 |
| 操作人 | `x-actor` 头，★ **只记录不校验**（权限在上层） |
| 店铺号 | ★ 全字段 **字符串** —— 18 位，JS 会精度丢失 |
| 未声明查询参数 | ★ **一律 400** —— 拼错的参数被静默忽略，返回的是「全量」而不是报错 |
| 错误形状 | ★ `{"error": "<code>", "hint": "<下一步>", …点名字段平铺在顶层}`（S-29，照 `service_social`；原 `{code, message, detail}` 作废）；★ **必须点名是哪几行**（如 `in_flight_rev` · `lines[]` · `allowed[]`） |
| 命名 | ★ 路径不用领星词汇：无 `inbound` / `shipment` / `allocation` |

### 0.1 状态码语义

| 码 | 用在 |
|---|---|
| 400 | 参数问题（缺字段、未声明参数、理由未填） |
| 404 | 对象不存在 |
| **409** | ★ **冲突与闸** —— 占用撞了、版本在流转、闸没过、水位变了 |
| 410 | 已废弃的接口 |
| 422 | 语义不合法（如非法状态迁移目标、由量推导的状态不许手动推进） |
| 502 | ★ 我们去查领星，**查询本身失败**（`lookup_failed`）：无法判断有无，不是「查无」 |
| 503 | ★ 维度镜像陈旧 → **拒绝服务**（E-4） |

★ **闸不过用 409 而不是 400**：400 是「你写错了」，409 是「你没写错，但现在不行」。
前端要能区分 —— 一个该改表单，一个该刷新重来。

#### 提交响应（`POST /v1/plans/{plan_id}/submit`，S-35 ~ S-41）

| 字段 | 含义 |
|---|---|
| `rev` · `in_flight` · `content_digest` | 新版号 · 是否在流转 · 提交时生效值的哈希。★ 内容完全相同的再提交仍立新 rev（S-43） |
| `lines` | 这次可铸出的格子数 = 保留 + 替换 + 新增 |
| `skipped[]` | `{sku, period, reason}`；`reason ∈ {empty_purchase, zero_purchase, no_claimed_msku}`（S-14） |
| `kept` | `{count, lines[{sku, period, line_id, state, total_units}]}` 没变，原记录换版 |
| `replaced` | `{count, lines[{sku, period, old_line_id, new_line_id, total_units{from,to}, demand_at_submit{from,to}}]}` 变了，旧的撤销、新的铸出 |
| `added` | `{count, lines[{sku, period, line_id, total_units}]}` 上一版没有 |
| `removed` | `{count, lines[{sku, period, line_id, total_units}]}` 这次铸不出，旧的撤销 |
| `split_frozen` | `{count, lines[{sku, period, line_id, split{from,to}}]}` 总量同、分店拆分变了，但记录已进采购：保留并冻结旧拆分（`split` 为 `{sid: units}`） |
| `left_completed` | `{count, lines[{sku, period, line_id, rev, total_units}]}` 已完结的记录这次不再包含：留在原版，不撤销 |

**409 `lines_in_purchase`**：`{error, hint, plan_id, lines[{sku, period, line_id, state, change, po_ids[], total_units{from, to}}]}`。
`change ∈ {replace, remove}`；`remove` 时 `total_units.to = null`；已完结的记录 `po_ids` 可为空。整次不生效，库里不留任何写入。
处置：改回原来的量，或先从采购单里移掉那条记录。

> `needs_verify`（带 `lookup_outcome` / `truncated` / `timeline`；查重命中却不能认时带 `landed_mismatch[]`）。事务② 前调用已被恢复收尾 → 按库里状态回 `placed` / `needs_verify`，带 `settled_by=recover`。`place` 的 409：`stale_confirm_token` · `preflight_failed`（带 `failed[]`；闸含 `single_wid` —— PB-D25 一张单只许一个仓）·
> `po_placing` · `po_frozen` · `po_discarded` · `needs_verify`。⛔ **任何分支都不自动重试**（`07` §2）。

```
POST /v1/purchase-orders/{po_id}/place
POST /v1/consignments/{cid}/dispatch
```

| 约定 | 为什么 |
|---|---|
| ★ 请求体必须带 `confirm_token`（由前一次 GET 返回） | 防误点、防重放 |
| ★ FBA 投送**每张排货单一次**二次确认（B-3） | **不可逆点是逐张跨的** |
| ★ 响应体**必须回显产生的全部外部单号** | 断在哪一步，前端看得出来 |
| ★ 部分成功要**明确表达**，不许当作失败 | 建单成功、发货失败 ≠ 什么都没发生 |

```jsonc
// 部分成功的响应形状
{
  "outcome": "partial",
  "steps": [
    {"stage": "create", "status": "ok",     "doc_no": "OWS2409170001"},
    {"stage": "lock",   "status": "ok"},
    {"stage": "ship",   "status": "manual", "reason": "timeout_needs_verify"}
  ],
  "our_stage": "已确认"     // ★ 未推进到已投送
}
```

★ **`outcome: partial` 这个形状是必须的**：
返回 200 会让前端以为全成了，返回 500 会让人以为什么都没发生 ——
**而真相是「建了单但没发货」，那张单真实存在于领星里。**

### 1.6 ★ G7 订正：`/v1/forecast` 的入参形状

你的原话是「**支持按日期查询，逐周的库存消耗情况，给出断货日**」——
所以入参是**查询起点 + 视野**，不是「月份区间」。

```jsonc
// POST /v1/forecast
{
  "as_of": "2026-09-16",          // ★ 从哪天起算（按日期查询）
  "horizon_weeks": 26,            // 逐周展开多少周
  "targets": [                    // ★ 上限 500（H-2）
    {"sku": "DCC1800264", "seller_id": "11072"}
  ],
  "plan_id": 42                   // 可选：把该计划的计划销量算进需求
}
```

```jsonc
// 响应
{
  "results": [{
    "sku": "...", "seller_id": "...",
    "weeks": [{"week_start": "2026-09-16", "opening": 820, "demand": 140, "supply": 0, "closing": 680}],
    "stockout_date": "2026-11-04",
    "days_of_cover": 49,
    "demand_source": {"history_weeks": 12, "plan_months": ["2026-10","2026-11"]}
  }]
}
```

★ **`demand_source` 必须回显** —— 「这个断货日是拿什么算出来的」，
不回显就没人能判断它对不对。
