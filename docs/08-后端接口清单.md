> **这份文档要做什么**
>
> 三份清单：★ **`api/ui/`**（给本仓前端）· ★ **`api/pub/`**（经 services 给 jxd_ai_ops）·
> **我们要对接的**（领星 / CH / PM）。
>

## 0. 约定

| 项 | 约定 |
|---|---|
| 前缀 | ★ 业务路由 `/v1`（`service.toml` 的 `path_prefix = "/v1"`） |
| 健康 | ★ `GET /health` —— **不加前缀**，探活目标 = `base_url + health.path` |
| 鉴权 | `x-internal-key`；★ 未配 → **启动失败**，不是运行时 503 |
| 操作人 | `x-actor` 头，★ **只记录不校验**（权限在上层） |
| 店铺号 | ★ 全字段 **字符串** —— 18 位，JS 会精度丢失 |
| 未声明查询参数 | ★ **一律 400** —— 拼错的参数被静默忽略，返回的是「全量」而不是报错 |
| 错误形状 | ★ `{"error": "<code>", "hint": "<下一步>", …点名字段平铺在顶层}`（S-29，照 `service_social`；原 `{code, message, detail}` 作废）；★ **必须点名是哪几行**（如 `in_flight_rev` · `lines[]` · `allowed[]`） |
| 命名 | ★ 路径不用领星词汇：无 `inbound` / `shipment` / `allocation` |

### 0.1 状态码语义

| 码 | 用在 |
|---|---|
| 400 | 参数问题（缺字段、未声明参数、理由未填） |
| 404 | 对象不存在 |
| **409** | ★ **冲突与闸** —— 占用撞了、版本在流转、闸没过、水位变了 |
| 410 | 已废弃的接口 |
| 422 | 语义不合法（如非法状态迁移目标、由量推导的状态不许手动推进） |
| 502 | ★ 我们去查领星，**查询本身失败**（`lookup_failed`）：无法判断有无，不是「查无」 |
| 503 | ★ 维度镜像陈旧 → **拒绝服务**（E-4） |

★ **闸不过用 409 而不是 400**：400 是「你写错了」，409 是「你没写错，但现在不行」。
前端要能区分 —— 一个该改表单，一个该刷新重来。

#### ★ grid 的预测块（2026-09-24，规格 `superpowers/specs/2026-09-24-plan-forecast-design.md` §6）

> 键名以 `api/ui/grid_forecast.py::_serialize` 为准，前端类型 `web/src/api/types.ts` 逐键对齐；
> 前后端共用的形状样本是 `tests/fixtures/grid_response.json`（= `web/src/api/fixtures/grid-1.json`，逐字节相同）。
> ★ 空 ≠ 0：下面凡是可空的数，`null` 都是「未知 / 不适用」，原因在同行的 `state` / `reason` 里。

| 键 | 粒度 | 内容 |
|---|---|---|
| `params` | 整张 | 本次用的规则：`as_of` · `route` · `make_days` · `ship_days` · `anchor_day` · `embargo_days` · `in_transit_as_of`（判在途「已逾期」用的快照日，`00` W-14）。★ 放响应体，不放 HTTP 头（计划 OP-6：头进不了 fixture） |
| `demand[].system_basis` | msku × 月 | 预测销量的依据（`03` `plan_demand_cell.system_basis`）；`null` = 旧认领没种（OP-8）；`reason = not_applicable_no_sales_source` = 预测不适用 |
| `forecast[]` | msku × 月 | `state`（`ok`/`partial`/`unknown`/`not_applicable`/`elapsed`）· `reason` · `unknown_since` · `opening` · `demand` · `inbound_planned` · `closing` · `stockout_date`（该月内首个断货日）· `basis{bridge, arrivals, as_of_start}`：`bridge` 是 as_of 次日到首月前一天的扣减（`by` = `forecast` / `first_month_expected`（`00` W-11）/ `unknown`，逐月 `segments[]` 给复算每一步），`as_of_start` 是 as_of 落在本月时的起点与那一段的 `segment` |
| `forecast_msku[]` | msku | `first_stockout_date`：整本台账（含桥接段）第一个断货日 |
| `forecast_store[]` | 店铺 × 货号 × 月 | = Σ 该店该货号的 msku 行；`system_not_applicable` 标「店里每个 msku 的预测都不适用」 |
| `forecast_sku[]` | 货号 × 月 | 库存 = Σ 有 FBA 的店铺；`stock_demand`（恒等式用）· `excluded_not_applicable` · `reason_from`（未知时是哪个 msku 让它未知）· `pipeline{making, shipping, ordered_open, ordered_open_overdue, ordered_open_sources[{period, units, ref, overdue}], fba_inbound: null, fba_inbound_reason: "not_fetched"}` · `in_transit` · `in_transit_excludes` · `unfilled_purchase[]`。★ `ordered_open_sources[].period` 是**预计到货月**（ETA），不是下单月 |
| `beyond_horizon[]` | 批次 | 计划采购到货落在推演窗外的，逐笔列（`arrives_after_horizon` / `arrives_before_as_of`） |
| `unallocated[]` | 批次 / msku | 分不出去的到货。共同核心键 `sku · order_period · arrive · units · reason`，`scope = batch`（整批没分，带 `unknown[]`）或 `msku`（分到了但该 msku 推演不了，带 `seller_sku · sid`） |

### 1.5 ★ 两个不可逆接口的额外约定

> `place` 的响应 `outcome` ∈ `placed`（带 `order_sn`）· `rejected`（带 `lx_code` / `lx_msg`）· `not_sent`（带 `cause`，可直接重试）·
> `needs_verify`（带 `lookup_outcome` / `truncated` / `timeline`；查重命中却不能认时带 `landed_mismatch[]`）。事务② 前调用已被恢复收尾 → 按库里状态回 `placed` / `needs_verify`，带 `settled_by=recover`。`place` 的 409：`stale_confirm_token` · `preflight_failed`（带 `failed[]`）·
> `po_placing` · `po_frozen` · `po_discarded` · `needs_verify`。⛔ **任何分支都不自动重试**（`07` §2）。

```
POST /v1/purchase-orders/{po_id}/place
POST /v1/consignments/{cid}/dispatch
```

| 约定 | 为什么 |
|---|---|
| ★ 请求体必须带 `confirm_token`（由前一次 GET 返回） | 防误点、防重放 |
| ★ FBA 投送**每张排货单一次**二次确认（B-3） | **不可逆点是逐张跨的** |
| ★ 响应体**必须回显产生的全部外部单号** | 断在哪一步，前端看得出来 |
| ★ 部分成功要**明确表达**，不许当作失败 | 建单成功、发货失败 ≠ 什么都没发生 |

```jsonc
// 部分成功的响应形状
{
  "outcome": "partial",
  "steps": [
    {"stage": "create", "status": "ok",     "doc_no": "OWS2409170001"},
    {"stage": "lock",   "status": "ok"},
    {"stage": "ship",   "status": "manual", "reason": "timeout_needs_verify"}
  ],
  "our_stage": "已确认"     // ★ 未推进到已投送
}
```

★ **`outcome: partial` 这个形状是必须的**：
返回 200 会让前端以为全成了，返回 500 会让人以为什么都没发生 ——
**而真相是「建了单但没发货」，那张单真实存在于领星里。**

### 1.6 ★ G7 订正：`/v1/forecast` 的入参形状

你的原话是「**支持按日期查询，逐周的库存消耗情况，给出断货日**」——
所以入参是**查询起点 + 视野**，不是「月份区间」。

```jsonc
// POST /v1/forecast
{
  "as_of": "2026-09-16",          // ★ 从哪天起算（按日期查询）
  "horizon_weeks": 26,            // 逐周展开多少周
  "targets": [                    // ★ 上限 500（H-2）
    {"sku": "DCC1800264", "seller_id": "11072"}
  ],
  "plan_id": 42                   // 可选：把该计划的计划销量算进需求
}
```

```jsonc
// 响应
{
  "results": [{
    "sku": "...", "seller_id": "...",
    "weeks": [{"week_start": "2026-09-16", "opening": 820, "demand": 140, "supply": 0, "closing": 680}],
    "stockout_date": "2026-11-04",
    "days_of_cover": 49,
    "demand_source": {"history_weeks": 12, "plan_months": ["2026-10","2026-11"]}
  }]
}
```

★ **`demand_source` 必须回显** —— 「这个断货日是拿什么算出来的」，
不回显就没人能判断它对不对。
