# 库存预测数学模型 — service_supplychain

> **这份文档要做什么**
>
> 给出一套**期望值公式**：把逐月**计划销量**与逐月**计划采购量**，
> 综合算成未来逐月的**可售库存**，让运营填完数**当场看见影响**。
>
> ★ 这一块**需求文档与原型此前都没有**。缺了它，「计划采购量」这一列
> 填了也白填 —— 原型实测：改采购量，**任何一个库存数都不动**。

## 0. 主公式

```
★  期末库存 = 期初库存 − 期望销量 + 当期入库量
```

★ **加项是「当期入库量」，不是「计划采购量」。**
采购的货要先穿过一条管道，**到期了才算进可售**。
把采购量直接加进库存，会得出「当月买当月就有」这种与现实相反的结论。

## 1. ★ 统计层级：每一行的最细颗粒度不同

> 合计视图里的每个数都是**统计上来的**。
> 统计过程本身就是模型的一部分 —— 不写清楚，合计行就成了第二个真相。

| 行 | ★ 最细颗粒度 | 合计怎么来 | 来源 |
|---|---|---|---|
| **期初 / 期末库存（可售）** | 店铺×msku（FBA）· 货号×市场（海外仓共享池） | 求和 | 计算 |
| **期望销量** | ★ **店铺×msku** | 求和 | 人填 |
| **当期入库量** | ★ **店铺×msku**（到货必有目的地） | 求和 | 系统 + 推算 |
| **货运中**（已发未到） | ★ **店铺**（发货单带目的仓） | 求和 | 系统 |
| **排货中**（已排未发） | ★ **店铺**（排货单带目的仓） | 求和 | 本服务 |
| ─────── | ─── ★ **排货这条线以下没有店铺** ─── | | |
| **本地仓在库**（待排货） | ★ **货号×国内仓，无店铺** | 本来就是货号级 | 系统 |
| **生产中** | ★ **货号，无店铺** | 本来就是货号级 | 推算 |
| **计划采购量** | ★ **货号，无店铺** | 本来就是货号级 | 人填 |
| **期间实际销量** | 店铺×msku | 求和 | 系统（次月回填） |

★ **那条横线不是模型画的，是「排货」这个动作画的** ——
排货就是给货指定店铺的那一刻。线以下的量**物理上还不属于任何店**。

### 1.1 ★ 恒等式（必须由代码强制，不是口头约定）

```
① 可售合计 ≡ Σ_店铺 可售        ← 合计行不许独立算一遍
② 在途合计 = 生产中 + 本地仓在库 + 排货中 + 货运中
③ 期末[m] ≡ 期初[m] − 期望销量[m] + 当期入库[m]     （每一层都成立）
④ 期初[m] ≡ 期末[m−1]
⑤ 某段流出 ≡ 下一段流入
⑥ 推算入库 ≡ 其构成明细之和
```

★ ①被破坏 = 两个真相；③在某一层不成立 = 那一层漏了一个流向。
落库与断言方式见 `03` §7。

## 2. 管道：货从下单到可售要穿过的四段

```
计划采购量 ─▶【生产中】─▶【本地仓在库】─▶【排货中】─▶【货运中】─▶ 当期入库 ─▶ 可售
   人填      make_days      完工即发       ——— ship_days ———
   货号        货号           货号×仓      ★ 店铺        ★ 店铺
                                            └────── 已定向 ──────┘
```

★ **管道阶段 = 业务真实阶段，不是另造一套**：
`排货中` 就是我们设计的**「已排未发」**，`货运中` 就是领星发货单**已发未签收**。
预测若自建一套阶段，两边永远对不上账。

### 2.1 管道递推

```
生产中[m]      = 生产中[m−1]   + 计划采购量[m]      − 完工入本地仓[m]
本地仓在库[m]  = 本地仓在库[m−1] + 完工入本地仓[m]    − 排货发出[m]
排货中[m]      = 排货中[m−1]   + 排货发出[m]        − 实际发运[m]
货运中[m]      = 货运中[m−1]   + 实际发运[m]        − 当期入库[m]
```

★ 每一段都是 `上期 + 流入 − 流出`，**流出必然是下一段的流入**（恒等式⑤）。

### 2.2 ★ 提前期按**天**配，而且是用户自己的变量

> **负责人裁定（2026-09-18）**
> 「具体几天我们都不知道，让运营和供应链自己设置。默认生产 30 天、运输 60 天，
> 实际允许用户调整。这样切到国内环境也能适配。」

| 参数 | 默认 | 含义 |
|---|---|---|
| `make_days` | **30** | 生产：下单 → 完工入本地仓 |
| `ship_days` | **60** | 货运：本地仓发出 → 目的仓可售（海外海运） |

预设只是**起点**，不是选项清单 —— 任意天数都能填：

| 档 | make / ship | 全程 |
|---|---|---|
| 海外 · 海运 | 30 / 60 | 90 天 |
| 海外 · 空运 | 30 / 10 | 40 天 |
| ★ 国内调拨 | 30 / 3 | **33 天** |

★ **单位必须是天，不能是月。** 月为单位表达不了「国内调拨 3 天」，
而那恰恰是切到国内环境时最该看见的一档。
★ 同理，「2 个自然月」按天算不是一个点、是 **62~90 天的区间** —— 这也是为什么必须按天。

### 2.3 ★ 天算、月显示：锚在**月中**

计划只说「10 月下单」，**没说 10 月几号**。要把天数落回月份，就得选一个锚点。

```
★ 锚 = 该月 15 号
```

| 锚点 | 后果 |
|---|---|
| 月初 | 「10 月下的单、生产 30 天、**10 月就完工**」—— 与直觉相反，且**系统性乐观**（把每笔单都当 1 号下的） |
| 月末 | 系统性悲观；还会把「国内调拨 3 天」一律推到下个月，**抹掉国内最该看见的「当月就到」** |
| ★ **月中** | 真实下单日在当月大致均匀分布，**期望值就是月中** —— 而这整套本来就是期望值模型 |

实测：

```
10 月下单 + 生产 30 天  →  2026-11 完工
10 月下单 + 全程 90 天  →  2027-01 可售
10 月下单 + 国内 33 天  →  2026-11 可售
```

### 2.4 ★ 计划周期也是变量

> **负责人裁定（2026-09-18）**
> 「默认未来 3 个月，但实际上也是变量，允许用户编辑，比如 6 个月、9 个月。
> 和生产、货运周期一样，属于一个默认配置，支持用户调整后重新计算格子。」

★ 它和提前期**归属不同**，不能放进同一个抽屉：

| | 归属 | 改它走哪 |
|---|---|---|
| `make_days` / `ship_days` | ★ **全局配置** | `setParams` |
| `plan_months` | ★ **这张计划自己的属性**（起点和长度本来就各不相同） | `setPlanMonths(planId, n)` |

全局的 `plan_months`（默认 **3**）只是**新建计划的默认值**。

**约束**：`1 ≤ n ≤ 24` 的整数。

★ **缩短周期会切掉已经填过的格子 —— 必须逐项点名，绝不静默清空。**
「少了几个数」在界面上是看不出来的。点名还要说清**改回去也找不回来**
（格子会重新长出来，但里面是空的），否则人会以为周期填回去数就回来了。

### 2.5 ★ 相容条件：周期与提前期会互相打架

```
第一个月下的单能落进周期内  ⟺  plan_months ≥ 全程提前期折合月数 + 1
```

★★ **这张表原先按「全程 90 天」算，已作废** —— 实测全程约 **122 天**
（采购段中位 **62 天**、n=1,062，见 `17`；加货运 60 天），折合 **≈4.1 个月**：

| 计划周期 | 第一个月的单 | 最后一个月的单 |
|---|---|---|
| **3**（默认） | ✗ **周期外** | ✗ |
| 4 | ✗ ← ★ **原先写的是 ✓** | ✗ |
| **5** | ✓ | ✗ |
| 6 / 9 | ✓ | ✗ |

★ **改了一个数，整张表的结论跟着变**：原先「4 个月就够」，实测要 **≥5**。
这正是默认值 30 天错得不止一格的地方 —— 见 §9.1。

★ **这不是缺陷，是现实**：全程 4 个月，做 3 个月的销售计划，
这张计划里下的单**本来就一件都赶不上**。

★ 但系统**必须把它说出来，并给出路** —— 界面要直接算出「填成几个月才够」，
而不是让运营对着一列不动的数字自己猜。

★ 同时要说清**最后一个月的单永远落在周期外**，无论周期拉多长 ——
计划末尾下的单本来就不该在本计划里见效。不说清，人会以为「拉长就全好了」。

## 3. ★ 分配：两个**独立**的决定，混在一起就会算错

> 这是实现时真正踩到的坑，写在最前面。

| 决定 | 答案 | 混淆的后果 |
|---|---|---|
| **发多少？** | ★ **完工即发（推式）**，不按缺口卡 | 按缺口卡 → 没人缺货的月份一件都不发，**货在管道里凭空消失** |
| **给哪个店？** | ★ **按缺口比例**；缺口吃不下时余量按期望销量摊 | —— |

★ 第一版把两者合成一个判断，结果 2026-12 的在途算出 **5 件**，
而负责人 Excel 里是 **110 件** —— 差的那 105 件不是算错了，是**被吞掉了**。

### 3.1 算法（两遍法）

```
第一遍 · 基线（只算已定向的量，完全不动未定向池）
    I⁰[s,m] = I⁰[s,m−1] + 已确认入库[s,m] − 期望销量[s,m]
    累计缺口 G[s,m] = max(0, −I⁰[s,m])

第二遍 · 逐批分配（按到货月从早到晚）
    一笔采购 = 一个批次： 下单 →(make_days) 完工 →(ship_days) 可售
    需求 N[s] = max(0, G[s, 到货月] − 已累计分给 s 的量)

    ΣN = 0      → ★ 谁都不缺，但货照发：全部按期望销量比例摊
    ΣN ≤ 这批货 → 先按缺口补齐，余量再按期望销量摊
    ΣN > 这批货 → 按缺口比例，取整，余数给缺口最大的那个

    ★ 断言：Σgive ≡ 这批货的件数。对不上就是管道漏货，宁可报错不许静默
```

★ 基线里的 `G` 是**累计**缺口，所以要减「已累计分给 s 的量」，
否则会重复补同一个窟窿。

### 3.2 ★ 依据必须说实话

```jsonc
// ✗ 第一版：rule 恒写「按缺口比例」，可 my_gap=0 的店分到了 107 件
{"rule":"按缺口比例","my_gap":0,"total_gap":5,"pool":600}

// ✓ 现在：记录**实际**怎么分的
{"gap_part":0,"weight_part":107,"my_demand":18,"total_demand":100,
 "rule":"缺口不足以吃下这批货：缺口部分 0 + 余量按期望销量摊 107","pool":600}
```

★ 一个自己都解释不了自己的数，比没有这个数更糟。

### 3.3 ★ 这与裁定 C4「不自动分摊」不矛盾

| | C4 管的 | 本模型做的 |
|---|---|---|
| 对象 | **执行** —— 真实排货怎么发 | **预测** —— 照计划走预期会怎样 |
| 裁定 | 不替人分摊，人看真实的数自己定 | ★ 必须假设一条规则，否则算不出来 |

★ 分配结果**不写任何表、不产生任何动作**，假设可见可改。
★ 反过来说，**完全不给模拟的代价是「这批采购对我这个店有没有用」永远没人能答**。

## 4. ★ 入库必须分两行：事实与假设不能混

负责人 Excel 里这一行标的是「系统检测」，**但未来月份系统检测不到** ——
只有已经发出的货才有预计到货日。由计划采购推出来的那部分是**假设**。

| 行 | 含义 | 性质 |
|---|---|---|
| `入库·已确认` | 已发运、领星有预计到货日 | ★ **事实** |
| `入库·按计划推算` | 由计划采购量经管道推出来 | ★ **假设** |
| `入库合计` | 两者之和 | 主公式用它 |

★ **一个数不能既是事实又是假设。** 混成一行，运营就分不清
「这批货真的在路上」和「这是我假设会到」—— 而这两者的处置完全相反。

## 5. ★ 外推的预估必须标明是外推

系统销量预估只覆盖前几个月。计划周期可以被拉到 6 / 9 个月，后面那些月**没有预估**。

| 做法 | 后果 |
|---|---|
| 当 `null` | 推演从第 4 个月起一律「未知」，**整条曲线作废** |
| 直接沿用最后一个值 | ★ 把**外推**冒充成**预估** |
| ★ **沿用 + 标记 `system_extrapolated`** | 可用，且人知道后面几个月的底是虚的 |

★ 这个标记**必须随推演结果一起返回**，不能让界面回头去读原始格子 ——
`system` 本来就是从格子派生的，**出处必须跟着数走**；两个来源迟早分叉。

## 7. 回测：期间实际销量

```
偏差[s,m] = 实际销量[s,m] − 期望销量[s,m]
```

★ 没有这一行，「期望销量」永远无法被证伪 —— 运营填得准不准、
哪个店系统性高估，谁都不知道，而这正是下次填数时最该看的东西。

| 要求 | |
|---|---|
| 次月系统回填，**不覆盖**原期望销量 | 两个数并排，才看得出偏差 |
| ★ 回填有滞后（订单是滞后采集的） | 标注「数据完整度」，**不要把不全读成低** |

## 8. 边界与守则

| # | 规则 | 为什么 |
|---|---|---|
| B1 | ★ **期望销量为空 ≠ 为 0** | 空是「需求未知」；当 0 算会得出「库存只涨不跌」 |
| B2 | ★ 未知从该月起**向后传染** | 基于未知算出的数更不可信 |
| B3 | ★ 到货月落在计划周期**之外**的采购，**显式列出** | 不许悄悄丢掉 |
| B4 | ★ 海外仓**共享池不并入任何单店** | 一个市场多店共用，各算一遍虚报一倍（裁定 C） |
| B5 | ★ 无 FBA 的平台显示「**不适用**」 | 不是 0 |
| B6 | ★ 本地仓在库**不进可售** | 国内仓的货几十天到不了目的仓，算进去是虚报 |
| B7 | ★ 分配结果**不写任何表、不产生任何动作** | 它是模拟的中间量，不是排货计划 |
| B8 | 负库存**如实显示为负** | 截断成 0 会把「缺多少」这个最重要的数抹掉 |
| B9 | ★ 管道每段的流出 ≡ 下一段的流入 | 对不上就是漏了货，要断言不要靠眼睛 |
| B10 | ★ 外推的预估要**带标记**；管道量**必须非负** | 「生产中 −5 件」没有物理含义，出现就是算错了 |
| B11 | ★ 缩短计划周期丢掉的格子**逐项点名** | 「少了几个数」界面上看不出来 |
| B12 | ★ 提前期/周期改动**立即重算**并回显 | 「将触发重算」而不给结果，等于没算 |

## 9. 算例（负责人 Excel 的数，逐格复现）

```
货号 DCC104132，5 店 3 平台（FBA 德/日/美 · shopify 北美 · tiktok 美）
```

| | 2026-09 | 2026-10 | 2026-11 | 2026-12 | 2027-01 |
|---|---|---|---|---|---|
| 期初库存（可售） | 500 | 400 | 413 | 372 | 270 |
| 期望销量 | 100 | 120 | 121 | 122 | 100 |
| 当期入库量 | 0 | 133 | 80 | 20 | 0 |
| **期末库存** | **400** | **413** | **372** | **270** | **170** |
| 计划采购量 | 0 | 110 | 111 | 112 | 80 |
| 货运中（= 表里的「在途」） | 233 | 100 | 20 | 110 | 221 |

★ 恒等式②在起作用：

```
在途[11月] = 20  ← 233 被 133/80/20 三笔正好排干
在途[12月] = 20 − 20 + 110（10 月采购）= 110   ✓
在途[1月]  = 110 − 0  + 111（11 月采购）= 221   ✓
```

★ **上表由 `forecast_demo.py` 逐格复现**（`EXCEL` 常量只用于对照，不参与计算），
合计的每个数都是从 5 个店铺的行 `SUM` 上来的。

### 9.1 ★ 一处对不上，值得记下来

```
--make-days 30  →  5 个月里只对上 1 个     ← 原产品默认值（★ 已被 B1 推翻）
--make-days 62  →  4/5                     ← B1 裁定值（实测 PO→首批收货中位，n=1,062）
--make-days 75  →  5/5 全中（六列含在途）  ← 负责人 Excel 隐含的交期
```

负责人表里「10 月的采购 110 件」出现在「12 月的在途」，反推生产是 **62~90 天**；
实测中位 62（`17`）与 Excel 隐含的 ≈75 **不是一个数** —— 中位数只是首批到货，Excel 记的更像整批。

★ **这处不一致曾被写成「不影响实现」—— 那是圆场，已删。** 两个独立来源都落在 30 的两倍以上，
