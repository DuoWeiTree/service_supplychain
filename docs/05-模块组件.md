## 0. 映射总则 —— 四层，四种构件

★ **本体的四层各自对应一种代码构件。哪一层不该变成类，代码里就不该有那个类。**

| 本体层 | 判据 | 代码构件 | ★ 不许是 |
|---|---|---|---|
| ① **对象** | 有身份、可描述、会被人查询 | **类型 + 表 + 仓储** | — |
| ② **关系** | 两对象之间，带基数 + 聚合语义 | **1:N → 外键**；**N:M 带数量 → 映射表 + 求和函数** | ★ N:M 不许用外键 |
| ③ **状态·事实** | 对象在某时刻的量，带 provenance | **派生属性 / 视图 / 冻结值对象** | ★ **不许是可变类** |
| ④ **动作** | 人做的事，产生 edit + 审计 | **函数**（用例） | ★ **不许是类** |

### 为什么这四条是可证伪的

| 若代码里出现 | 说明 |
|---|---|
| `class Submission` | 「提交」是④动作 → **它不该是类，只该是 `submit()`** |
| `class Inventory` 且可变 | 「在仓量」是③事实 → **它会变成第二个真相** |
| `plan_line.po_id` 外键 | 承重墙①是 N:M 带数量 → **外键等于强行 1:N，而 1:N 是错的基数** |
| `class StockLevel` 带 `update()` | 同上，事实不许可变 |

★ **这张表就是本文的自检项**。`tests/test_ontology_mapping.py` 逐条查（见 §6）。

## 1. ① 对象 → 类型 + 表 + 仓储

### 1.1 一个对象在代码里有三样东西

```
类型      shared/contracts.py 里的 frozen dataclass —— 跨模块传递的形状
表        scm.<table>          —— 03 已定义
仓储      repo/<aggregate>.py  —— ★ 唯一允许写这张表的地方
```

★ **「仓储」这一层的存在理由只有一条：把「谁能改这张表」收敛到一处。**
散落的 `INSERT` 会让「这条记录怎么来的」查不出来 ——
而那正是出问题时唯一有用的信息。

### 1.2 聚合根与从属实体

★ **聚合根 = 事务边界。** 从属实体**不单独持有仓储**，跟着根一起写。

| 聚合根 | 从属实体 | 仓储 | 为什么是这个边界 |
|---|---|---|---|
| **销售计划** `Plan` | 草稿格子 · 格子 msku 构成 · 认领 | `repo/plan.py` | 格子只在计划里有意义；改一格是一个事务 |
| **计划单** `PlanRev` | **计划单记录** `PlanLine` | `repo/plan_rev.py` | ★ **提交是一个事务铸出全部记录** —— 半铸的计划单无法解释 |
| **采购单** `PurchaseOrder` | 采购单明细 | `repo/purchase.py` | 一单一供应商，整单冻结 |
| **排货表** `Sheet` | — | `repo/sheet.py` | 确认闸是**整表级**的 |
| **排货单** `Consignment` | 排货行 | `repo/consignment.py` | ★ **投送是逐张跨不可逆点的** |

★ **`PlanLine` 不是聚合根，但它有独立状态** —— 这不矛盾：
状态由**事件表**推进，而事件表的写入仍然经 `repo/plan_rev.py`。
**「有状态」与「是聚合根」是两件事。**

## 2. ② 关系 → 两种实现，由聚合语义决定

★ **关系怎么实现，由「能不能求和」决定，不由基数决定。**

### 2.1 映射规则

| 关系形态 | 代码实现 | 例 |
|---|---|---|
| 1:N，从属 | **外键** + 从属实体列表挂在根上 | 计划 → 格子 |
| 1:N，**不得求和** | 外键，★ 且**禁止提供 `sum()` 便利方法** | 货号 → 库位库存 |
| N:1，引用 | 外键，只存 id | 采购单 → 供应商 |
| ★ **N:M 带数量** | **独立映射表 + 求和函数** | ★ **两条承重墙** |

### 2.2 承重墙在代码里是什么

★ **一张表 + 一个求和函数 + 一个恒等式，三样缺一不可。**

```python
# ① 映射表（03 §4.1 / §5.1）
scm.po_source_map        (po_id, line_no, line_id, units)
scm.dispatch_source_map  (consignment_id, sku, from_wid, line_id, units)

# ② 求和 —— ★ 唯一入口，别处不许自己写 SUM
# rules/quantity.py
@dataclass(frozen=True)
class LineQty:
    total: int
    confirmed: int      # 承重墙① 求和
    ordered: int        # 承重墙① 求和，限已下单
    staged: int         # 承重墙② 求和，排货单 ∈ {草稿, 已确认}
    dispatched: int     # 承重墙② 求和，排货单 ∈ {已投送, 已归档}

    @property
    def pending(self) -> int:
        return self.total - self.staged - self.dispatched

# ③ 恒等式 —— 返回违反了哪几条，★ 不返回 bool
def check_invariants(q: LineQty) -> list[str]: ...
```

★ **「别处不许自己写 SUM」是这条映射的要害**：
各处自己 SUM，早晚有一处忘了过滤旁路终态（已撤销 / 已放弃）——
于是**待排量被永久扣掉一块，那批需求再也排不出去，而界面只显示「待排 0」**。

所以求和只在 `scm.v_plan_line_qty` 视图里发生一次，`LineQty` 只是它的搬运工。

### 2.3 「不得求和」怎么在代码里表达

```python
# ★ 三地库存分开持有，类型上就不给你相加的机会
@dataclass(frozen=True)
class StockByNode:
    by_wid: Mapping[int, int]
    # ★ 刻意不提供 total() —— 国内仓的货 35 天到不了 FBA
```

★ **把「不得求和」写成注释没有用，要写成「没有那个方法」。**

## 3. ③ 状态·事实 → 派生，不建可变类

| 事实 | 代码形态 | ★ 为什么不是类 |
|---|---|---|
| 各种量 | `LineQty`（frozen，视图搬运） | 存下来就有两个真相 |
| 计划单整体状态 | `derive_overall(lines)` 纯函数 | 派生**每次读时算，永远不会分叉** |
| 在仓 / 可发 / 在途 | `StockByNode`（frozen） | 它是 CH 的快照，不是我们的状态 |
| 领星进度 | `scm.v_ext_current_stage` 视图 | ★ **`max(stage_rank)` 派生 → 结构上不可能倒退** |
| 预测结果 | `ForecastResult`（frozen） | ★ 函数返回值，**不落库** |

★ **唯一两个「事实被物化」的地方**：`plan_line.state` 与 `consignment.our_stage`。
它们之所以能物化，是因为有**事件表 + 触发器 + 禁止直改**三道锁 ——
**没有这三道锁的事实，一律不许物化。**

## 4. ④ 动作 → 函数，不建类

★ **动作在代码里是 `usecase/` 下的函数，不是类，不是表。**

| 动作 | 函数 | 产生什么 |
|---|---|---|
| 提交 | `usecase/submit_plan.py::submit()` | 铸出 `PlanLine` + `plan_submit_skip` 留痕 |
| 组单 | `usecase/build_po.py::build()` | 承重墙①映射 + 触发再评估 |
| 下单 | `usecase/place_po.py::place()` | `order_sn` + `ErpCall` |
| 确认排货表 | `usecase/confirm_sheet.py::confirm()` | 过闸 → 冻结 |
| 投送 | `usecase/dispatch.py::dispatch_one()` | `ExtRef` × N + `ErpCall` × N |
| 撤销 | `usecase/cancel.py::cancel_line()` | 事件（★ 理由必填） |

### 4.1 一个动作函数的形状

```python
def place(po_id: int, actor: str) -> PlaceResult:
    """★ 动作函数的四段式，顺序固定：
    1. 取状态并锁行      repo 层
    2. 问判据            rules 层 —— ★ 不在这里写 if
    3. 做副作用          erp 层（出站）或 repo 层（本地）
    4. 记事件与审计      repo / erp
    """
```

★ **第 2 步「不在这里写 if」是关键**：
业务判断一旦写进动作函数，就**只能靠起一套环境来测** ——
而动作函数是最难造场景的地方（要有计划、有记录、有草稿、有凭证）。
判据必须在 `rules/`，动作函数只负责**去问**。

★ **`usecase/` 里不许有类**。出现 `class SubmitPlanService` 就说明
④层被当成①层建模了 —— 而**动作没有身份，没人会去查「第 123 号提交」**。

## 5. 模块划分 —— 是上面映射的结果

### ★ 5.0 前端也在本仓（Q-1）

| 构件 | 落点 | 约束 |
|---|---|---|
| 页面（按角色） | `web/src/pages/` | 三个角色共用**同一张网格心智模型**（`10` §2） |
| 数据层 | ★ `web/src/api/` | ★ `mock \| api` 可切换（Q-6） |
| 视觉 | `web/src/styles/` | ★ 墨迹系统，纯 CSS，从原型原样带来 |
| BFF | `api/ui/` | ★ 随界面变，不进契约 |
| 对外契约 | `api/pub/` | ★ 暴露结论，不暴露内表 |

★ **前端不承载领域判据** —— 判据在 `rules/`，前端只**展示**它的结论与依据。
在前端复制一份判据，就会出现两个真相，而界面那份没人测。

```
shared/contracts.py     ①对象的类型 · ③事实的 frozen 值对象
rules/                  ②关系的求和 · ③的派生 · 判据      ★ 纯
forecast/               预测（移植）                      ★ 纯
repo/                   ①对象的仓储（唯一写表处）
usecase/                ④动作
erp/                    出站 + ExtRef/ErpCall 仓储        ★ 唯一出站写
dim/                    CH 取数 + 维度镜像                ★ CH 只读
api/                    HTTP 壳：路由 · 状态码 · 事务开合
jobs/                   回执器与定时
```

★ **`api/` 只剩一层薄壳** —— 因为动作在 `usecase/`、判据在 `rules/`、写表在 `repo/`。
旧项目 `plan.py` 1871 行，正是因为这四件事全挤在接口文件里。

### 5.1 一个请求穿过哪几层

```
api/          解析 · 开事务 · 翻译错误码
  └ usecase/  四段式
      ├ repo/    取与写
      ├ rules/   判据
      └ erp/     出站（仅需要时）
```

## 6. ★ 映射的自检 —— `tests/test_ontology_mapping.py`

> 映射会走样，而走样**不会报错**。所以要能自动查。

| # | 检查 | 对应本体规则 |
|---|---|---|
| M1 | `usecase/` 下**没有 class 定义** | ④动作不许是类 |
| M2 | `shared/contracts.py` 里③层类型**全是 `frozen=True`** | 事实不许可变 |
| M3 | `plan_line` / `consignment` 之外**没有表带 `state` 列却无配套事件表** | 物化事实必须有三道锁 |
| M4 | 承重墙两张表**没有被任何外键从 `plan_line` 指过来** | N:M 不许退化成 1:N |
| M5 | ★ 全仓 `SUM(units)` **只出现在 `v_plan_line_qty` 视图** | 求和唯一入口 |
| M6 | `StockByNode` **没有 `total` / `sum` / `__add__`** | 不得求和写成「没有那个方法」 |
| M7 | 每个①对象**有且只有一张主表、一个仓储** | 对象不许有两个落点 |
| M8 | `repo/` 之外**没有 `INSERT INTO scm.`**（`erp/` 的两张除外） | 写表收敛 |

★ **M5 与 M8 是这套映射能不能守住的关键**。
它们防的是同一件事：**「就在这里顺手写一句」** ——
每一次顺手，都在给下一个「数对不上」埋种子。
