排货单 · 详情

手动排货还是自动排货？——「全手动」，系统只算该排多少，不替你决定发什么

全手动。系统只算「该排多少」：这一格的缺口、这条计划记录还能排多少、 本地仓现在还能安排多少。发哪些、从哪个仓出、给哪个店 —— 全是人定的， 系统一件都不会替你摊。

这是裁定 C4「不自动分摊」的直接后果：同一个货号常常挂着好几个店铺， 谁先谁后、各拿多少，只有排货员知道。系统替人摊过一次， 就再也说不清那批货当初是为谁排的。

入口只有一个：上面那张排货网格。在某一格上「安排发货」， 量先进待编排池；池子平时收着，要一次性编入排货单时才展开。 安排过的格子上会多出「改」和「撤回」—— 改数量是一步，不是撤回再重排。

口径与判据

这张网格和销售计划的网格是同一个东西：店铺 · 货号 × 月。 每格里四个数分别是 销售预估（机器估的）、 期望销量与计划采购（人填的）、 以及推演出来的库存预估（格子里那个大数）。 已安排是这一格已经落地的排货量。

哪些数能加，哪些不能：一个店铺下可能挂着多个 msku，销售预估 / 期望销量 / 库存预估 按 msku 求和；计划采购是货号级的，不带店铺也不分 msku，所以不求和； 已安排按「计划记录 × 店铺」记，同一个店铺的几个 msku 共用一份，也不求和。 加错了会把同一批量数出两三倍。

合计列里，销售预估 / 期望销量 / 计划采购 / 已安排是逐月求和； 库存不是流量而是水位，求和没有意义，所以那一栏给的是期末库存（最后一个月）。

格子左边条：红＝库存预估见底，浅红＝当月备货接不住期望销量，绿＝这一格已经安排过发货。 三者同时成立时红压浅红、浅红压绿，因为断货比「已安排」更需要先被看见。

排货表与排货单：一张排货表（SHEET-xx）是一次排货作业； 作业里一个目的地一张排货单。在网格上「安排发货」得到的量先进待编排池， 再编入某张排货单。池里的量已经算进「已排未发」 —— 不算就会把同一批需求排两遍。

网格与池子是一条路的两步，不是两个入口：所以池子默认收起，只在要 一次勾好几行、一起编入排货单时才展开。安排 / 改 / 撤回三件事走的是同一条路 —— 一次操作整体决定这一格安排多少，改成 0 就等于撤回。三条路各有各的校验，迟早会对不上。

弹窗里给三个数：仓里有多少（物理量）、其中多少已被别处安排还没发出、 现在还能安排多少。只给一个「可发 24」，两种完全不同的状态就长得一模一样了。

FBA 与海外仓的单据形状不同：海外仓一张备货单从头走到尾（3 步）； FBA 是多个对象接力（5 步），中间多一步「STA 建货件」，所以 FBA 的排货单上多出 「货件号」与「装箱」两栏，海外仓那张根本没有这两栏。

货件号不用填，也填不出来：它是亚马逊在 confirmPlacementOption 之后才返回的（不轮询 taskId 就不知道），而人看到这张表是在投送之前 —— 那一刻这个号还不存在。所以这一栏只读：投送前写「投送时由亚马逊分配」， 投送时那一步取回号再回填进来。投送前没有号是正常状态，不是漏填。 真正要人填的只有装箱（裁定 A-8）—— 运营说的「关联货件麻烦」不是流程绕， 是装箱数据量大。

提交排货会一次跑完 6 项闸（G1 装箱 / G2 建货件的前置 / G3 可发量 / G4 账本水位 / G5 未关联发货 / G6 目的地），过的也逐项列出来。不过闸时状态不变，仍是草稿。 G2 查的是目的地齐不齐（店铺 + FC）——「每行已归属货件」那条查不了， 跑闸的那一刻号还不存在；「发货前必须已归属货件」改在投送链内部、 发货那一步之前检查，那时号刚取回来。 G4 / G5 在原型里恒过，真实实现要比对账本水位与领星侧未关联发货单。

保存草稿：每一次改动其实都已经立刻存进浏览器，这个按钮只是再存一次并给一个时间戳。 投送不可逆，中途失败时前几步产生的单据是真的存在于领星里 —— 所以结果逐步列出，停在哪一步、已经落了哪些单号都点名。
