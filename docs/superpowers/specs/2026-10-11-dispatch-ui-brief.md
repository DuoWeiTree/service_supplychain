## 0. 为什么要重新设计（负责人 2026-10-11 试用原话）

> 「目前的交互太过于混乱！」
> 「采购单和销售计划中都存在 DCC1041294BW，而我们在排货时，整体操作毫无头绪，**用户根本不知道自己是否完成了
> 销售计划对应的需求**，只能靠用户自己记忆：哪个销售计划需要多少货，对应的货是否采购完成，库存是否满足。」
> 「我搜索出来的货号，完全没有库存信息！」（原因：每行把 38 个本地仓各列一列，几乎全是 0，真数被挤到屏幕外）

★ 设计要回答排货员的**三个问题**，一眼能看到，不靠记忆：

1. **这张计划还差多少没排？**（按记录，也按整张计划）
2. **差的这些，货在哪？** —— 采购到哪一步了（组单 / 下单 / 入库 / 待到货），本地哪些仓真有货、能用多少
3. **我刚排的这些，变成了几张排货单、发去哪、还缺什么才能确认？**

## 1. 一句话

运营的**销售计划**提交后变成若干**计划记录**（货号 × 月 × 总量，带各店期望）。采购员按记录下**采购单**，货陆续到**本地仓**。
排货员**选一张未完成的销售计划**，把本地仓的货**按 msku（店铺的 listing）**安排到**目的地**（FBA 本店，或某个海外仓），
系统自动按目的地拆出**排货单**；FBA 行补装箱；过 6 道闸后**确认**（之后才能提交给领星，下一阶段）。

```
销售计划 ──提交──▶ 计划记录（货号 × 月 × 总量）──采购单──▶ 领星采购单 ──到货──▶ 本地仓库存
                                   │                                          │
                                   └────── 排货表（一张表 = 一张计划）◀───────┘
                                              │  人：每格 = 来源仓 · 目的地 · 件数
                                              ▼
                                系统派生：排货单（每个目的地一张）→ 确认 →（C-b/C-c）提交领星
```

## 2. 对象与关系

| 层 | 东西 | 说明 |
|---|---|---|
| 对象 | **销售计划** | 计划名 · rev（版本）。排货的入口单位（CA-D11：**一张排货表只对应一张计划**） |
| 对象 | **计划记录** | 货号 · 月 · 总量 · 各店期望（参考，不是配额）· 状态（§3.3） |
| 对象 | **排货表** `sheet` | 一次排货作业，挂一张计划。状态 草稿 / 已确认 / 已取消 |
| ★ 人的输入 | **格子（安排）** | **唯一由人填的东西**：(记录 或「无计划来源」) × 店 × msku × **来源仓** × **目的地** × 件数 |
| 对象 | **排货单** `consignment` | ★ **系统派生，人不建不删**：每个 (渠道, 目的地) 一张 —— FBA 按店（FC 由亚马逊投送时才分，不在键里）；海外仓按仓。单号 `SCM-CN-{id}` |
| 对象 | **排货行** | 排货单 × msku × 店 × 来源仓 × 件数，件数 = 计划来源 + 无计划来源 |
| 人的输入 | **装箱** | 只有 FBA 排货行有：箱数 · 长 · 宽 · 高 · 单箱重量 · 单箱件数 |
| 对象（外部） | **采购单 / 领星采购单** | 只读引用：单号 · 状态 · 本记录下了几件 · 领星行项的已入库 / 待到货 |
| 状态·事实 | **本地仓库存** | 每个本地仓 × 货号 × **桶**：共享桶 + 各店铺桶。来自 ClickHouse，带「截至」日期 |
| 动作 | 新建排货表 · 填 / 改 / 撤回格子 · 填装箱 · 确认 · 取消（要理由） | 每个都留谁 · 何时 |

量的语义（设计要表达对，但**不要合成新数**）：

| 量 | 挂在 | 怎么来 |
|---|---|---|
| 需求 | 记录 | 记录总量 |
| 已组单 / 已下单 | 记录 | 采购单来源求和（草稿算已组单；已下单只算下到领星的） |
| 已入库 / 待到货 | 记录关联的已下单采购单（同货号**整单**的行项） | 领星行项 `quantity_entry` / `quantity_receive`；★ **不摊回记录**（一张单可能服务多条记录） |
| 已排未发（本表 / 别表） | 记录 | 所有未发排货单里这条记录的件数 |
| 已投送 | 记录 | C-a 恒为 0（还没有提交） |
| **还差** | 记录 | 需求 − 已排未发 − 已投送；0 = 已满足 |
| 本地可发 | 货号 × 本地仓 × 桶 | 领星 `product_valid_num`（只读这一列） |
| **可安排** | 货号 × 本地仓 × 店 | 本店桶 + 共享桶 − 已承诺（含别的排货表）；**负数 = 已超** |

★ **需求侧（还差）与物理侧（本地可发 / 可安排）是两种量纲，并排显示，不相减成一个「可排量」**（`10` 原则三）。

## 3. 状态

### 3.1 排货表

| 状态 | 能做的事 |
|---|---|
| 草稿 | 改格子 · 填装箱 · 确认 · 取消 |
| 已确认 | 全部冻结；只能取消（要理由）。（C-b 起这里出现「提交领星」） |
| 已取消 | 只读；它占的量全部释放 |

### 3.2 排货单（跟随排货表，人不直接操作）

草稿 → 已确认（随表确认）→（C-b）已投送 → 已归档；草稿 → 已放弃 / 已确认 → 已取消（随表取消）。

### 3.3 计划记录（参考，**不拦排货**）

已提交 → 已确认（全部组单）→ 已下单（全部下到领星）→ 准备排货（首批良品入库，★ 未实现）→ 已排货 → 已完结；任意 → 已撤销。

★ **按量排（CA-D10）**：只要不是 已撤销 / 已完结，就能排，上限 = 还差。状态只作展示 ——
例：DCC1041294BW 需求 180、已下单 5、记录停在「已提交」，但本地已有 565 件，**照样能排**。
已撤销的记录若本表还有格子：照样列出、标「记录已撤销，只能撤回」，确认会被挡。

## 4. 端到端任务流（排货员视角）

1. 打开「排货」：看到**未完成的销售计划**（每张：记录数 · 需求 · 已组单 · 已下单 · 已排未发 · 已投送 · 还差）。
2. 选一张计划 →「按这个计划排货」（这张计划已有草稿表则接着那张）。
3. 在计划的记录清单里，挑「还差 > 0」的记录；看它的采购 / 入库进度和本地哪些仓有货。
4. 对记录下的某个店 × msku：选**来源仓**（只列真有货的仓，可安排多的在前）· **目的地**（FBA 本店 / 海外仓）· **件数** → 回车或离开即生效。
   - 同一个 msku 可以从两个仓发、也可以一部分去 FBA 一部分去海外仓 → 多格。
   - 件数清空 = 撤回这一格。
5. 系统即时派生排货单；排货员看到「本表现在有几张排货单、各发哪、多少件」。
6. FBA 排货单的每一行填装箱。
7. 「确认排货表」→ 6 道闸一次列全；过了就冻结。不想要了 →「取消排货表」（要理由）。
8. 计划里没有、但本地有货想一起发的 →「无计划来源库存」里按货号 / msku 搜，同样填格子。

## 6. 业务规则（设计不能绕开）

| # | 规则 | 出处 |
|---|---|---|
| 1 | **一张排货表 = 一张销售计划**；只能排这张计划的记录（另加无计划来源库存） | CA-D11 |
| 2 | **按量排**：记录未撤销 / 未完结即可排；同一条记录全部排货表合计 ≤ 总量（超了后端 409 `over_total` 并给出 总量 / 已用 / 本次） | CA-D10 · `04` §7.4 |
| 3 | 计划来源的格子：**店必须是这条记录里出现的店**；msku 可以是该店该货号的任一 msku | CA-D6 |
| 4 | **无计划来源**：本地任何可发库存都能排，不要求理由；单独记账（排货行上分「计划来源 / 无计划来源」两列） | CA-D2 |
| 5 | **分配单位是 msku**（店铺 listing），不是货号 | CA-D3 |
| 6 | **目的地逐格选**：FBA = 本店（店有 FBA 才有这个选项）；海外仓 = 列表（按店铺市场过滤，市场未知的仓也列） | CA-D5 |
| 7 | **库存桶**：给店 X 能用的 = 共享桶 + X 自己的桶；别的店的桶不能用 | CA-D8 |
| 8 | 来源仓只能是**本地仓** | CA-Q19 暂行 |
| 9 | 超出可安排量**写时只警告**，确认时 G3 才挡 | CA-Q20 暂行 |
| 10 | 排货单由格子**自动派生**：每个 (渠道, 目的地) 一张（FBA = 店，不到 FC）；改格子即时重派生；人不能建 / 删 / 改排货单 | N-3 |
| 11 | **装箱只给 FBA 行**；海外仓行**没有**装箱这一栏（不是禁用，是不存在） | `10` §4 |
| 12 | 挪格子（改来源仓 / 目的地）撞上已有格子 → 409 `cell_exists`（不悄悄覆盖人填的量），让人去改那一格 | 终审 I1 |
| 13 | 确认后整表冻结；取消要理由，释放占用 | CA-D7 · `04` §4.2 |
| 14 | 确认要带上「我看到的水位」（防止确认别人刚改过的表） | G4 |

## 7. 确认闸（六道，一次全列）

| 闸 | 查什么 | 不过时谁修 |
|---|---|---|
| G1 | FBA 行装箱字段齐全 | 人：在排货单上填装箱 |
| G2 | FBA 排货单有店铺 | 系统 / 人：回格子重选目的地 |
| G3 | 本地可发够（按桶判）；★ 库存读不到 = 「无法判定」，不放行（确认返回 503） | 人：减少安排或换来源仓 |
| G4 | 自你打开后，别的排货表没改过同一 货号 × 来源仓 | 人：刷新核对后再确认 |
| G5 | 疑似未关联的发货 —— ★ **待裁定 · 未检查**（显示为「？」，不拦） | — |
| G6 | 目的地合法 | 人：改目的地 |

闸项形状：`{gate: "G1".."G6", ok: true | false | null, code, detail, fix}`。`ok: null` = 无法判定 / 未检查，**不能显示成通过**。
另：确认前若这张表在核对视图里有问题（如记录已撤销），返回 409 `dispatch_check_failed` + `violations[]`。

## 9. 文案与数据约定

- 错误响应形状：`{error, hint, …点名字段平铺在顶层}`；前端已有 `ErrorDetail` 组件照原样点名。
- **空 ≠ 0**：库存读不到写「未知」、采购行项没读到写「未读到」，不写 0。
- 「已满足」只在还差 = 0 时出现。
- 成功提示用「已 + 动作原词」（已保存装箱 / 已确认排货表 / 已取消排货表）；失败不出 toast，原地点名。
- 页面文字里不出现 ` · ` 这种元串分隔（已有测试 `copyDiscipline`）。

## 11. 给设计的边界

### 可以自由设计

- 整体版面与导航：计划总览 → 计划工作台的结构、分步 / 分栏 / 抽屉 / 弹层，一屏还是多屏
- 记录进度的呈现方式（表格、卡片、进度条形式都可以 —— 但见下「不能合成」）
- 格子的编辑方式：按记录 → 店 → msku 的层级、按仓、按目的地、批量填、「把还差全排给这个店」之类的便捷动作（只要最后落成单个格子 `PUT`）
- 排货单面板与装箱的位置；闸列表的位置；无计划来源库存的入口形态
- 筛选 / 排序（只看还差 > 0、只看本地有货的、按仓…）

### 不能动（领域约束，不是审美）

| 约束 | 来源 |
|---|---|
| **先选计划再排**；一张排货表只对一张计划 | CA-D11 |
| 人只填**格子**；排货单**只读派生** —— 不出现「新建排货单 / 删除排货单 / 把行挪到某张单」 | N-2 · N-3 |
| **需求侧与物理侧并排，不合成「可排量」「完成率」**；还差就是还差，可安排就是可安排 | `10` 原则一 · 三 |
| 海外仓行**不渲染**装箱栏（不是禁用） | `10` §4 |
| 闸**一次列全**，点名到行；`ok: null` 不显示成通过 | `10` 原则五 |
