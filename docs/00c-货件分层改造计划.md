## 2. 命名待定（O-5）

★ `shipment` 是**领星占用词，已禁用**（`CLAUDE.md` 命名隔离），而 `02` §511 记着
它自己就一词两义（FBA 头程发货单 / 亚马逊货件）。所以新表不能叫 `consignment_shipment`。

| 候选 | 取舍 |
|---|---|
| ★ `amz_shipment` / `amz_shipment_line` | 前缀把「哪个 shipment」问清楚了，禁用令的本意（消歧）达到 |
| `parcel` / `parcel_line` | 不撞词，但 parcel 更像「箱」，与装箱概念再撞一次 |

✅ **已定（O-5，09-21）**：`scm.consignment_split` / `scm.consignment_split_line`，中文仍叫**货件 / 货件行**。

★ 决定性的理由不是好看，是**渠道中性**：负责人问「是不是要按 amazon/walmart/海外仓分开操作」——
不是。排货员面对的永远是排货单/排货行；**海外仓恒 1 行、FBA N 行**，差异是数据不是代码分支。
所以 `amz_` / `fba_` 前缀都不能用（我第一轮推荐 `amz_shipment` 是错的）。

避开：`shipment`/`allocation`（领星禁用）· `parcel`/`box`（与装箱撞）· `lot`（与效期批次撞，
货件明细里真有 `release_date`/`expiration`）。

## 3. ★ C-6：不用等领星实调了（09-21 实测）

原问题：`confirmPlacementOption` 的**同步返回**里有没有逐行明细？
★ **换条路就绕过去了** —— 明细在**采集侧**已经有：

| 表 | 实测 |
|---|---|
| `lingxing_fba_shipment_list_items` | **16,930 行 / 893 货件 / 440 货号**（09-01~09-21，**10 个采集日**） |
| 字段 | `shipment_id` · `sku` · `msku` · `quantity_shipped` · `quantity_received` · `ware_house_storage_id` |
| `lingxing_fba_shipment_list` | `destination_fulfillment_center_id`（★ FC）· `sta_inbound_plan_id` · `sid` |

★ **实测直接推翻了 `02` 的 N:1**：

```
货件含多货号   814 个
★ 货号进多货件  414 个     ← N:M 在生产数据里是真的
```

### 但它是**回读**，不是同步返回 —— 三条约束跟着来

| # | 约束 |
|---|---|
| 1 | ★ 投送成功与拿到货件归属**不是同一时刻**：中间有一段「已投送、归属未知」的窗口。这正是**两轴状态**该表达的东西，不许用一个字段掩盖 |
| 2 | ★ 采集面必须先验覆盖：**10 个采集日 / 21 天**，有缺口。`quantity_received` 用**下限判据**（外部物理事实），`quantity_shipped` 才是我们投出去的量 |
| 3 | ⚠️ **残留缺口**：排货行的键含 `from_wid`，而货件明细里只有 `ware_house_storage_id`。同一货号从两个本地仓发货时，**行→货件的拆分可能对不回去** —— 这一条仍要实调，且**不许猜分摊** |

★ 所以 **S2b 解阻，但承重墙③ 的恒等式要按 `quantity_shipped` 立，并允许「归属未知」这一态**。
