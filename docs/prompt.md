【运营侧 · 销售计划】

运营员工操作销售计划的核心目的是提供需要下单的需求信息！
1. 运营建一张计划（标题、计划周期月、跨几个月[默认未来3个月]）
2. 选货号(支持删除重新添加) → 认领 msku(支持删除重新添加)。下单之前，一个产品作为一条有独立状态的记录，只能属于一个计划（认领即占用）
3. 系统按 店铺 × 货号 × 月 给出销量预估建议值（整数）；同一张表还有「计划采购量」列，当计划采购量变更后需要，重新计算基于该计划量的逐月库存预测，在没有用户确认前，计划采购量默认复制系统预测的销量作为初始值。
4. 运营只改要改计划采购量的格子，没改的直接用系统值（逐格「采纳」已废除）
5. 提交 → 冻结整张计划 → 生成一张计划单（rev），状态 = 已提交
6. 计划单全手动流转：已提交 → 已确认 → 已下单 → 准备排货 → 已排货 → 已完结；管理员可撤销须写理由；一个计划同时只能有 1 版在流转，支持标记当前使用版本(默认是最新版本为当前使用)。请注意： 销售计划的状态与备货表的状态不同，备货表有独立状态！ 销售计划的记录，也就是对应的货品、店铺记录也是实体，有独立状态，计划单的整体状态会受到记录状态影响。
7. 运营可以重新加载已保存的销售计划表，检查自己的销售计划，支持建立新版本。
8. 销售计划交互界面中，需要体现核心指标，当前进行中的销售计划数量(未完结的都属于进行中)，已提交数量、已提交但未确认、已下单、准备排货、已排货的销售计划状态数量，支持查询哪个运营用户的销售计划还未提交。


【供应链侧 · 销售计划】

供应链员工在操作销售计划的核心目的是整理出需要下单的货品信息,并查询销售需求货品对应的进度，进度在哪个环节？ 是否正常？ 是否可能逾期，导致断货！？

**提交需求信息流程**
1. 在运营提交销售计划后，供应链员工可以看到所有销售计划，可以通过状态筛选找到近期"已提交"的销售计划。
2. 通过选择运营提交的确认销售计划，可以联合查看，将多份销售计划整理到一个表格界面中检查，方便供应链根据货品、货品分类、时间（年月），分组检查需求数量。
3. 供应链员工可以将所需的确认数量的货品信息，根据货品、数量、供应商，将需要下单的货品信息整理成采购单（一份采购单是多个货品与数量对应一个供应商的确认下单清单，独立实体有自己状态，未来用于对接ERP实现自动操作，目前由人工维护），当货品被整理成采购单时，销售计划表里的需求货品记录状态转为"已确认"，而采购计划整个对象的状态由所有子记录决定，只有所有子记录转为已确认，采购计划的状态才应该转为已确认，同理，已下单等状态也是。供应链员工可以查询已创建的采购单，采购单的调整必须在已下单状态前操作，一旦下单则快照为已下单表中，已下单后不可变更。
4. 只有供应链员工可以在已确认的销售订单的记录下查询关联的采购单，采购单拥有“下单”动作，支持下单操作（需要挖掘lingxing ERP下采购单的API具体操作）。 已下单是指该采购单内的对应货品下单，这里会出现同一个货品分供应商分开下单的情况，也就是分别为部分下单，这要独立思考。
5. 下单后，等待工厂生产，工厂生产后对应的产品会补充本地仓货品数量，我们可以通过lingxing ERP的入库单追踪订单号对应货品与数量，确保单据链路一致，在本地仓库存查询对应货品数量得到补充即可完成接下来的排货工作。

**查询销售计划进度**
1. 运营登录可根据销售计划列表，直观看到货品执行进度，判断是否符合需求，如果发现有问题！ 仅作为查询进度使用。
2. 支持下钻关联具体的排货情况，从自己的销售计划表，关联货品记录的下单、排货、发货、到货详细情况。

【供应链侧 · 排货】

供应链员工操作排货的核心目的是管理lingxing ERP备货单，并统一规划创建发货单，让一次远程货运的效率更高，杜绝重复发货！

**安排排货数据**
lingxing ERP的备货单是一个完整的功能，我们要先接入api接口，确保对备货单的调用，不需要我们自己建立备货单，我们需要管销售计划，通过需求计划安排备货单所需的数据，用来创建和管理lingxing备货单。(要注意平台仓的操作原理和概念是与备货一样的逻辑，但是操作方式不同，见下方的差异说明，我们要整合成一个排货概念，平台仓和非平台仓的处理联合成我们项目的同一套操作，但底层根据目标使用不同逻辑)
1. 供应链员工可以从2个维度查询备货情况，一是从已有采购计划作为入口，查询采购计划的记录对应的订单，订单对应的入库单与本地仓库存; 二是从已有本地仓库存作为入口，筛选对应货品数量信息。
2. 两种入口都可以选择对应货品（选择时可以确认发货用from的仓库ID），并选择目标仓库(FBA要求选择的是店铺或站点，海外仓选择的是仓库ID），开始创建一张的排货表待配货状态(FBA使用的是发货计划，而海外仓直接是创建备货表)，对排货表实体进行编辑操作（lingxing备货单对应的操作接口所需数据需要确认）; 注意，平台仓FBA等于是在绑定对应的货件单号，而非平台仓则是为备货单中发货动作准备数据。
3. 从候选列表选择添加行：候选 = 从采购计划入口为状态为「已下单 / 准备排货」的计划单对应货品，按 店铺 × 货号 汇总剩余周期需求（跨计划累加），目的是识别是否有跨计划表的相同货品
4. 每行建议量 X = 需求 − 在库 − 在途 − 已排未发；源 = 国内仓(可多仓)，目的地 = 该店铺库位(FBA与海外仓参数不同)，在操作时，比较优秀的做法是左右两个框，左侧是发货信息选择(可选从销售计划或仓库入口, 编辑从该仓发货数量)， 右侧是发货单目的地的发货单记录，这样操作时就可以从左边视为发货侧，右边视为收货侧，必须选择一个发货单进行操作该过程，完成一份发货单草稿的创建，创建发货单草稿后，此时并没发货，因此对应的销售计划与货品状态为已排未发(对应危险处理见下)。
5. 确认排货表(一份排货表是由N张发货单草稿或发货单构成)。两道闸：「疑似未关联的发货」必须清完；期间别的排货表动过「已排未发」→ 409 要求重建
6. 确认后，可对排货单的发货单逐一创建发货单动作，非平台仓的海外仓是直接使用lingxing ERP的备货单对应的发货动作接口; 而平台仓FBA，则是直接操作发货接口, 创建发货单(从草稿转为正式发货单时，根据接口要求填写对应的发货信息，FBA直发是必填追踪信息)。此后对应的发货单、排货表、销售计划记录、销售计划的状态会变化，流转为"待收货"。
7. 发货后，外部的数据采集系统会每日采集数据，对应的发货单状态变化也会更新，当发货单处于“已完成”，则可以检查对应仓库的入库记录是否能对上（amazon FBA可以通过发货单 SP… → 货件 FBA… → FC 入库 判断是否完结，而海外仓可以通过 备货单 OWS… → r_wid判断状态完成)

**关于已排未发的处理**

## 1. 核心模型

库存有两个**互不相同**的事件，必须分开建模：

| 事件 | 效果 |
|---|---|
| 锁定 allocate / lock | `可用量 ↓`，`总量` 不变 |
| 扣减 deduct | `总量 ↓` |

三个区间：

| 区 | 定义 | 风险 |
|---|---|---|
| **A 区** | 已建单、**未锁定** | **最高**。库存视图中完全不可见，是重复发送的唯一来源 |
| **B 区** | 已锁定、未扣减 | 标准「已排未发」。可用量已反映，可控 |
| **C 区** | 已扣减、未收货 | 在途，不可逆 |

**关键事实 `[V]`：三个建单接口全部不锁库存** —— `CreateShipmentPlan`、`createReadySendOrder`、`CreateInbound`。
因此「单建好了 ≠ 库存被占住了」。A 区必须由排货表自己兜住。

## 2. 库存动作时刻表

### 2.1 FBA（平台仓）

| 接口 | Path | 库存动作 | 依据 |
|---|---|---|---|
| 创建 FBA 发货计划 | `/erp/sc/routing/storage/shipment/createShipmentPlan` | 不动 | `[V]` 全文无扣减/锁定字样 |
| 发货计划锁库存 | `FbaPlanStorageAllocate` | **锁定** | `[V]` 「支持按发货计划单号批量锁定库存」 |
| 发货计划释放库存 | `FbaPlanStorageRelease` | 解锁 | `[V]` 「支持按发货计划单号批量释放库存」 |
| 生成待发货的发货单 | `/erp/sc/routing/storage/shipment/createReadySendOrder` | 不动 | `[V]` 全文无扣减/锁定字样 |
| 发货单分配库存 | `ShipmentLockStock` | **锁定** | `[V]` 「只锁定库存数量，发货时按先进先出匹配出库批次」；`lock_batch=1` 锁到具体批次 |
| 发货单释放库存 | `outboundOrderReleaseStock` | 解锁 + 状态回退 | `[V]` 「待发货状态的发货单，释放库存后，将流转为待配货状态」 |

| **生成已发货的发货单** | `/erp/sc/storage/shipment/createSendedOrder` | ★ **建单即扣** | `[V]` 「推送已发货的FBA发货单到领星ERP，并扣减发货仓库库存」 |

### 2.2 海外仓（非平台仓）

| 接口 | Path | 库存动作 | 依据 |
|---|---|---|---|
| 创建备货单 | `/erp/sc/routing/owms/inbound/createInbound` | 不动 | `[V]` 全文无扣减/锁定字样 |
| 备货单分配库存 | `/basicOpen/overSeaWarehouse/stockOrder/allocate` | **锁定** | `[V]` 错误示例：「锁定库存出现异常…仓库可用库存不足」 |

## 3. 外部状态枚举（完整，勿凭记忆补全）

### 3.1 海外仓备货单 `lingxing_warehouse_oversea_stock_list.status` `[V]`
10 待审核   20 已驳回   30 待配货   40 待发货   50 待收货   51 已撤销   60 已完成
- `CreateInbound` 只能创建 `40` / `50` / `60`；`10`/`30` 由系统内部流转产生 `[V]`
- 无审核/驳回/撤销接口，`10`/`20`/`51` 程序无法驱动 `[V]`
- 收货仓为三方 API 海外仓时，创建状态只会到 `40` `[V]`
- `listInbound` 提供 `sub_status`（仅 `status=50` 生效）：`0 全部 / 1 未收货 / 2 部分收货` `[V]`
  → **`status=50` 内部混有部分收货，不可当作「一件未收」**

### 3.2 FBA 头程发货单 `lingxing_shipment_list.status` `[V]`
-1 待配货   0 待发货   1 已发货   2 已完成   3 已作废   4 已删除
- 生产实测：`1`=392 张、`3`=1 张，**`-1`/`0` 恒为 0**；`2 已完成` 从未出现
- 送达判据用 `delivery_date` 非空，**不可用 `status`**

### 3.3 亚马逊货件 `lingxing_fba_shipment_list.shipment_status` `[V]`
WORKING  READY_TO_SHIP  SHIPPED  IN_TRANSIT  CHECKED_IN  RECEIVING  DELIVERED  CLOSED  CANCELLED
- 分界：`SHIPPED` = 承运人已取件 = 已发
- `DELIVERED` ≠ 已入库：实测 220 行 4719 件，`quantity_received` 全为 0
- `is_synchronous`：`0` ERP 创建 / `1` 亚马逊后台同步

## 6. 硬规则

### ① 可发量只读 `product_valid_num`，禁止自行用总量相减

CH 表 `jxd_raw.lingxing_inventory_warehouse`：

| 列 | 含义 |
|---|---|
| `product_valid_num` | 可用量（已扣除锁定） |
| `product_lock_num` | 锁定量 = 已排未发 |
| `good_lock_num` / `bad_lock_num` | 良品 / 次品锁定量 |
| `quantity_receive` | 待到货量（采购在途） |

类型均为 `Nullable(Int64)`，聚合前需 `ifNull(x,0)`。

生产实测（最新采集日）：7854 行中 206 行有锁定，`sum(product_lock_num)=5132`、`sum(product_valid_num)=152118`。
`wid=36782` 锁 3320 / 可用 978（锁定量为可用量 3.4 倍）—— 若按总量排货必然重复发送。

### ② A 区必须限时清理

`is_locked=false` 且 `created_at` 超阈值的行 → 告警。
理由：建单接口不锁库存，该批货在领星库存视图中不可见，任何并发排货方都会认为它可用。

### ③ 不可逆边界：两条路径不对称

| | 可退回手段 | 不可逆点 |
|---|---|---|
| FBA | `outboundOrderReleaseStock`（解锁 + 退回待配货）；`FbaPlanStorageRelease` | `SendGoods` / `CreateSendedOrder` |
| 海外仓 | **无解锁接口**；仅 `DeleteOverSeaStockOrder` 删单（限 `status ∈ {10,20,30,40}`），删单是否释放锁定 → `[U]` | `SendInbound`（之后不可删、无撤销接口） |

→ 海外仓不可逆点更早、更硬，排货表对 `channel=oversea` 应采用更保守的阈值与二次确认。

### ④ STA 建货件是真实的亚马逊写操作

`/amzStaServer/openapi/**` 全族为 Amazon SP-API Fulfillment Inbound v2024 透传 `[V]`：
`createInboundPlan` / `listPackingGroupItems` / `setPackingInformation` / `generatePlacementOptions` /
`confirmPlacementOption` / `cancelInboundPlan` / `task-plan/operate`。
`confirmPlacementOption` 处产生真实亚马逊货件；失败重试会建出重复货件。
**按 path 前缀判定副作用**：`/amzStaServer/` = 打到亚马逊；`/erp/` = 仅改领星本地（如 `updateShipmentActualStatus`、`syncShipment`）。

## 7. 对账口径（建议每日执行）

### 7.1 A 区敞口（核心指标，理想值 0）

```
库存侧：SELECT from_wid, sum(ifNull(product_lock_num,0)) FROM jxd_raw.lingxing_inventory_warehouse FINAL
        WHERE _captured_date = (SELECT max(_captured_date) FROM jxd_raw.lingxing_inventory_warehouse)
        GROUP BY wid

单据侧：SELECT from_wid, sum(qty) FROM 排货表 WHERE stage = 'LOCKED' GROUP BY from_wid
```

差额 = 建了单但未锁库存的规模 = 重复发送敞口

### 7.2 排货表 vs 外部状态（防状态漂移）

| 路径 | 外部查询 | 当前基线 |
|---|---|---|
| 海外仓 | `lingxing_warehouse_oversea_stock_list FINAL WHERE status IN (30,40)` | 7 单 / 5175 件 |
| FBA 货件 | `lingxing_fba_shipment_list FINAL WHERE shipment_status IN ('WORKING','READY_TO_SHIP')` | 32 货件 / 790 行 / 11169 件 |

**FBA 头程发货单层恒为 0 的成因** `[V]`：880/880 货件 `is_synchronous=1`（亚马逊后台创建后同步），
392 张发货单全部为「已发货」。该租户的 FBA 流程是「亚马逊后台建货件 → 发货 → 领星事后记账」，
领星头程发货单不承担事前排货职能。
→ **排货表对 FBA 应以「亚马逊货件」为锚，不要以领星发货单为锚。**

**其他**:

目前 lingxing_fba_shipment_plan_list 里是几乎空的，原因是目前我们供应链员工是没有创建备货计划的，是直接通过线下确认的excel上传到备货表里，直接确认的，供应链员工给的说明也非常直接，因为之前没有线上操作，关联操作在lingxing里收到操作太麻烦了。 而我们要实现的就是在排货的简单易懂的操作。

并且也没再lingxing erp里进行FBA创建货件，原因也是关联操作太麻烦了。 这是我们项目必须要认真思考如何让关联货件操作变简单。

销售计划单 / 采购单 / 计划采购量 的关系是: 销售计划单 与 计划采购 可以看作一个实体，而计划采购量是指具体的采购货品对应的数量， 而采购单，则是下单采购的实体，与销售计划不同。

```
§6 同时要求这两条。若流转中的是 rev2、用户把 rev3 标成"当前使用"，排货该读哪一版？需求按哪一版算？ 不定死，排货候选会取到两个不同的数。
```

在发货前，以当前使用为准计算，而发货后，快照的是计算使用的版本，发货对应的版本是不可更改的，否则会导致已经发货了，但是用户改变了当前使用，那计算方式就错了！


```
「只有所有子记录转为已确认，整体才转已确认」。那部分怎么表达？"10 个货号里 7 个已下单、3 个还在等报价"是常态，现在计划单只能停在"已提交"，看板上那 7 个已经在走的完全看不见。
```

我的考虑是基于用于使用的感受，一个销售计划中，包含N货号，N个对应采购单，如果有一个已提交，而其他的都没变化，此时的整个销售计划状态，应该是已提交？还是不变呢？ 我觉得只要明确一种统一口径的方式即可，如果要添加部分态，则可能会导致数据更复杂。

```
正常采购量是 需求 − 在库 − 在途 − 已排未发。默认复制销量预估，等于忽略手上已有的货。运营不逐格改就会照"从零开始备"下单。要么默认值改成扣减后的建议量，要么界面显式标注"此值未扣减在库"。
```

默认复制销量预估，这是基于用户使用的角度，因为销量预估是计算的字段，而该字段，如果没有复制系统推荐，则会都为0，而用户则要每个单元格都修改销量预测的值，这会让用户抓狂，而提供默认值，则可以很大程度减少用户的操作。这是为了交互考虑。


我觉得最大的难点是在如何兼容排货阶段的， 平台仓和非平台仓，接口不同，但是原理相同的兼容问题。 我们需要实现一套基于我们系统的排货功能，而又要能直接联动lingxing的备货单，对于不能联动备货单的，还要使用发货计划，发货单等独立功能完成。
因此，我们的系统有一套完整的排货对应的数据结构，而操作动作使用的是lingxing对应的接口。

这里还有要注意的是，数据同步问题，联动lingxing ERP的接口是实时且可写的，但是效率低，合适直接操作的动作。 而CH的数据jxd_raw，我们有在后台进行同步采集，因此直接读CH更快，但是数据有延迟(至少1天)，并且只能用于分析，不可写，且不合适高并发访问(需要额外的视图处理)。
