## P1 · 格子拆成两张表

**发现**：一个数不可能既是当月的减项（销量）又是两个月后的加项（采购）。
它们**粒度也不同**：期望销量跟 listing 走，采购量跟货号走。

| 表 | 主键 | 字段 |
|---|---|---|
| `plan_cell_demand` | `(plan_id, seller_id, seller_sku, sid, period)` | `system_units`（建议）· `demand_units`（运营填）· `touched` |
| `plan_cell_purchase` | `(plan_id, sku, period)` ★ **不带店铺** | `purchase_units` · `touched` |

★ `touched` 不是冗余：**没它就分不清「人填的」和「跟随系统建议的」**，
一次「加个 msku」会把人辛苦改的数悄悄覆盖掉（原型实测踩到）。

**落点**：`03` §2.1 拆表 · `02` §3.1b · `08` 的 `PUT /cells` 拆成两个端点。

## P2 · ★ `plan_line` 不带 `seller_id`

**这是影响最广的一条。**

计划单记录按**货号 × 月**铸出，`seller_id = NULL` —— 因为**供应链下单不关心店铺**，
「这批货给哪个店」要到**排货**时才定（负责人原话）。

连带后果：

| 受影响的 | 原来 | 现在 |
|---|---|---|
| **承重墙①** 采购来源映射 | 指向 (店铺,货号,月) 的记录 | 指向 (货号,月) 的记录 |
| **承重墙②** 排货来源映射 | 同上 | 同上；**店铺信息在排货单的目的地上** |
| **排货候选** | 「按 **店铺 × 货号** 汇总剩余周期需求」 | ★ **按货号汇总**，店铺在排货时才选 |
| `plan_line` 新增 | — | `demand_at_submit`（合计）· `demand_by_seller`（jsonb，冻结当时各店铺期望销量） |

★ **`demand_by_seller` 不是冗余**：采购量是货号级的，但「这批货当初是为哪几个店备的」
只有提交那一刻知道 —— 不冻结，事后永远还原不出来。

**落点**：`03` §2.3 / §4.1 / §5.1 · `02` §2.4 关系表 · `06` §3.1 候选口径 · `08` 候选接口。

## P3 · ★ 库存拆三份，用途不同

| | 粒度 | 用在哪 |
|---|---|---|
| **FBA 在仓** | msku | ┐ **可售库存** —— 库存预测扣它 |
| **海外仓在仓** | ★ **货号 × 市场**（共享池） | ┘ ★ **单列，不并入任何单店合计** |
| **本地仓在仓** | 货号 × 国内仓 | ★ **不进可售**；只用于排货确认闸 G3 |

★ **本地仓再多货也不进可售** —— 国内仓的货 35 天到不了 FBA，算进去就是虚报。
★ **共享池不并入单店** —— 一个市场多个店铺共用，各算一遍就虚报一倍（裁定 C）。
★ **无 FBA 的平台**（Walmart 等）显示「**该平台无 FBA**」，**不是 0** —— 0 与「不适用」是两回事。

**落点**：`02` §3.1a（已补）· `03` 新增 `stock_fba` / `stock_oversea` 两张镜像表。

## P4 · ★ 提前期进模型

```
到货月 = 下单月 + 提前期（生产 + 头程）
```

★ 10 月下的单 12 月才到。**不建模提前期，会得出「越买当月库存越多」这种与现实相反的结论。**
★ 到货月落在计划周期**之外**的那几笔，**必须显式列出**（「2026-11 下单 140 件 → 2027-01 才到，对本计划无帮助」），不能悄悄丢掉。

**落点**：`02` §3.1b（已补）· `03` 提前期作为配置项 · `06` §1.1 流程图。

## P6 · ★ 排货表要有「待编排池」

**发现**：捡进排货表但还没编进排货单的量，**必须计入「已排未发」** ——
不计就会把同一批需求**排两遍**，正是确认闸 G4 要拦的那类错。

新增 `sheet_pool(sheet_id, line_id, sku, from_wid, units)`，
且 `lineQty` 要单列 `pooled`，界面能区分「捡了没编排」。

**落点**：`03` §5 · `02` §2.2.1 · `06` §3.1。

## P7 · ★ 投送必须断点续跑

**发现**：重投是从头跑全部步骤 → **每次重投都新建一遍单据**。
原型里实测堆出 10+ 张重复单号。

```
正确：dispatch 先读已有 ext_ref，★ 已拿到单号的步骤一律跳过，只续未完成的那一步
```

★ 「重投会重复建单」这句警告**是我们自己的实现造成的，不是领星的毛病**。

**落点**：`01` §5.1 · `04` §4 · `07` §5 · `08` §1.5。

## P8 · ★ 缺「人工核实」动作

**发现**：文档到处写「超时转人工，绝不自动重试」，
**却从没设计「人工核实完了怎么把结论告诉系统」** —— 于是超时是个死胡同。

新增动作 **UC-D13 人工核实超时投送**：

| 结论 | 后果 |
|---|---|
| `sent` 领星侧其实已发出 | 推进到「已投送」，扣库存 |
| `not_sent` 确实没发 | 允许重投；★ 已建单据跳过，只补发货那一步 |

**落点**：`04` 白名单加边 · `07` 时序 · `08` 接口 · `09` 用例。

## P9 · ★ 排货只能进不能出

**发现**：捡货、编排、建排货单**全是只增**，没有任何移除口子。
人按「待排量」捡多了 → 确认闸拦住 → 捡进去的量已算进已排未发 → **候选里消失** → **既过不了闸又回不去**。

缺三个接口：

```
DELETE  待编排池的一行
DELETE  排货单里的一行（退回池子）
DELETE  整张排货单（空单）
```

★ 这正好撞上 `04` §6 自己立的规矩：**「状态机能画出的退回边，必须真的退得回去」** ——
这里连画都没画。

**落点**：`08` §1.3 · `09` UC-D 补用例。

## P10 · ★ 「同一计划同时只 1 版在流转」做不到 —— 待裁定

**发现**：旧版里**已经在流转的记录撤不掉**（货可能在做、钱可能已付），
所以「换版必须先撤销旧版」执行不了。原型实测两版可同时在流转。

| | 做法 | 代价 |
|---|---|---|
| **A** | 旧版有记录在流转 → 提交**直接拒**（409） | 忠于原设计；但一个货号已下单就锁死整张计划三个月 |
| **B** | 允许多版并存，这条约束**作废** | 灵活；但排货候选要跨版累加 |

★ 倾向 **B** —— A 在业务上站不住。**待你裁定。**

## P11 · 目录必须搜索式

真实库成百上千个货号，**全列出来让人挑从第一天就是错的**。

| 要求 | |
|---|---|
| 不给条件 → **故意不返回**（`needQuery`） | ★ 与「查不到」必须**长得不一样** |
| 命中超上限 → `truncated`，提示细化 | 不硬塞一屏 |
| 「被占用」的行**留在表里标红**，不过滤 | 过滤掉，人永远不知道「我要的那个为什么没出现」 |

**落点**：`08` 目录接口加 `limit/truncated/needQuery` · `09` UC-O2 · `10` 交互原则。

## P12 · 草稿要能保存并接着干

每改一格立即落库；界面**常驻「草稿已保存 · 时间」**，写失败时显式报「没有保存」。

★ 原型里还实测到一条：**改了数据结构就重置，等于把人的草稿干掉**。
正式实现里对应的是**迁移**——迁得动的迁，迁不动的**逐项点名**，不静默清空。

**落点**：`09` UC-O3/O4 后置条件 · `10` 交互原则。

## P13 · ★ 整套库存预测数学模型缺失

**发现**（负责人原话）：**「你实现的原型，改了计划采购，并不会影响库存，
只是显示将在 12 月到货，但是对库存的影响呢？」**

★ 属实。原型里计划采购量只进 `pool_months`（本地仓池子），
**永远到不了任何店铺的可售库存** —— 于是整列数字是死的，运营看不到「这么买够不够」。

★ 更要紧的是：**需求文档里也没有。** P1~P4 只写了「格子拆两张表」「提前期进模型」，
**从没写过期初、期望销量、入库量、管道各段之间的方程**。

**补法**：新增 `14-库存预测数学模型.md`，主公式

```
期末库存 = 期初库存 − 期望销量 + 当期入库量      ★ 加项不是「计划采购量」
```

并按负责人手做的 `docs/库存预测计算方式.xlsx` 补上**四段管道**与**统计层级**。

### ★ 连带：数据库必须能复现负责人那张表

负责人原话：**「我必须要能从数据库里统计该表！否则我根本无法核实你计算的准确性！」**

★ 判据因此不是「算得对」，而是 **「别人能不能自己查出来核对」**。
新增 7 张表（`03` §7 · 35~41），其中三条是结构性的：

| | |
|---|---|
| ★ **没有合计表** | 合计只由视图现算 —— 存了就是第二个真相 |
| ★ **「排货以下没有店铺」做成 CHECK** | 不是注释，写错了插不进去 |
| ★ **`v_forecast_check` 返回 0 行才算对** | 每轮推演必跑，非空整轮作废 |

**落点**：`14`（新）· `03` §7（新）· `02` §3.1b · `00` M 组。

## P14 / P15 · ★★ 同一条判据的两个方向

**P14 发现**（负责人 2026-09-19）：排货表头写「已编排 3 行 / 52 件」，
而排货网格上**每一格都是「已安排 0 件」**。

**P15 发现**（同日）：确认闸要求每行填 FBA 货件号，界面长出一个 `FBA16XXXXX` 输入框 ——
> 「怎么可能有呢！这是要去 FBA 创建后、读取回来信息才能知道。货件号都没创建，怎么关联？」

★ **两个 bug 是同一条判据的两个方向**：

```
★ 凡是某一步的产出，在后续每一步的对象上都必须**必填**。
```

| 方向 | 后果 | 实例 |
|---|---|---|
| 该必填的判成可空 | ★ 货**悄悄消失**，界面显示成「一件都没有」 | P14：排货行缺店铺归属 |
| 不该必填的判成必填 | ★ 要一个**还不存在**的东西，流程卡死 | P15：确认闸要货件号 |

★ **两种错都不会报错，都只会「看起来正常」。**

### 为什么 P14 不是实现走样

`02` 的排货行主键此前就是 `(consignment_id, sku, from_wid)`，**本来就没有店铺**。
原型是忠实地实现了一份欠定义的文档。

★ 负责人原话：**「这种关键的关系，必须在文档里约束！否则这是原型错误了我还能发现，
但实际实现生产代码禁止出现相同的错误！」** —— 所以修法是改**约束**，不是加运行时检查。

### P15 的根因是一条裁定被扩大了适用范围

A-8 裁定的是「**装箱数据**人工填写」。实现时把它扩到了**货件归属**上。
而货件号是 `confirmPlacementOption` 之后才返回的（`02` §488、`07` §337）。

★ A-6「排货行**发货前**必须已归属货件」的检查点因此在**投送链内部**
（「发货」那一步之前），**不在确认闸** —— 确认闸跑在投送之前。

**落点**：`02` §3.5（判据升到本体层）· `03` §5.0 + `consignment_line` + 承重墙②
· `04`（A-6 的阶段位置）。

## P16 · 两条链的「目的地」不可类比（外部带回，2026-09-21）

> 来源：**数据部门**，不是原型踩出来的 —— ★ 这是第一条由外部独立验证发现的错。

| | |
|---|---|
| 他们说的 | 海外仓 `r_wid` 必填、我们说了算；FBA 的 FC 在 `confirmPlacementOption` 之后才知道，且**一批货可能被拆成多个货件分到不同 FC**。按「一个目的地一张」建模，FBA 这条会错 |
| 我们错在哪 | ★ 把**货件**当成了排货行上的一个字段（`ext_shipment_no`），而它在 `02` §488 早已登记为**对象** |
| 同一份文档自相矛盾 | `02` §488/§645 写着 **1:N 必须求和**，而 §8 行写着「一个目的地一张」 |
| 病灶同源 | 与「缺 `dispatch_arrangement`」一样：**没有落点的东西被塞进了别的对象** |
| 改造计划 | ★ `00c-货件分层改造计划.md`（S0~S6，S2b 阻塞于 C-6） |

★ **为什么原型没抓到**：原型只跑了「1 个货件」那条路（`16` §4 的 S4）——
**覆盖不到的代码不会失败，所以也不会报警。**
