## 1. 运营提交计划

```mermaid
sequenceDiagram
    autonumber
    participant UI as 前端
    participant API as API
    participant RULE as 规则层
    participant FCST as 预测函数
    participant PG as PostgreSQL
    participant CH as ClickHouse

    UI->>API: POST /plans 建计划
    API->>PG: INSERT plan
    PG-->>API: plan_id

    UI->>API: POST /plans/{id}/mskus 认领
    API->>PG: INSERT claim（部分唯一索引裁决）
    alt 已被「尚未下单」的计划占用
        PG-->>API: unique_violation
        API-->>UI: 409 msku_already_claimed + 占用方 plan_id / actor
    else 通过
        PG-->>API: ok
        API->>PG: seed 网格壳（店铺 × 货号 × 月）
        Note over API,PG: ★ 店铺没挂渠道 → 建不出格子<br/>必须显式数出来并点名，不许静默少一批
    end

    API->>CH: 取该 货号×店铺 的历史真实销量
    CH-->>API: 销量序列
    API->>FCST: forecast(货号 × 店铺, 月份区间)
    FCST-->>API: 系统预估销量（逐月）
    API->>PG: 写格子 system_value，planned_units 默认复制
    API-->>UI: 网格

    UI->>API: PUT 改某格 planned_units
    API->>PG: UPDATE cell（★ 一格一事务）
    API->>FCST: 重算该 货号×店铺 的逐月库存预测
    FCST-->>API: 断货日 / 逐周消耗
    API-->>UI: 新曲线

    UI->>API: POST /plans/{id}/submit
    API->>RULE: select_submittable(格子集合)
    RULE-->>API: 可提交集合 + skipped[] 逐条理由
    API->>PG: BEGIN
    API->>PG: INSERT plan_rev(rev = N)
    Note over API,PG: ★ 单版流转由部分唯一索引裁决<br/>不是先查后写
    alt 已有一版在流转
        PG-->>API: unique_violation
        API->>PG: ROLLBACK
        API-->>UI: 409 another_rev_in_flight
    else 通过
        API->>PG: INSERT 全部计划单记录（state = submitted）
        API->>PG: 标记 rev N 为「当前使用」
        API->>PG: COMMIT
        API-->>UI: rev N + skipped[]
    end
```

**读这张图要看什么**

| 看点 | 为什么 |
|---|---|
| 第 5 / 26 步两处冲突**都由库层裁决** | 先查后写在并发下必然漏，而且漏的时候不报错 |
| `skipped[]` **逐条理由**回给前端 | 静默跳过 = 运营看到一张「看起来正常」的计划，而缺的那批正是最该被看见的 |
| 提交是**一个事务**铸出全部记录 | 半铸的计划单无法解释 |
| 改一格是**一格一事务**，重算在事务外 | 预测慢不该把行锁攥着 |

## 2. 供应链组单 → 下单

```mermaid
sequenceDiagram
    autonumber
    participant UI as 前端
    participant API as API
    participant RULE as 规则层
    participant PG as PostgreSQL
    participant GW as ERP 网关
    participant LX as 领星

    UI->>API: GET /plan-lines?state=submitted 联合查看
    API->>PG: 按 货品 / 品类 / 年月 分组
    PG-->>API: 记录集
    API-->>UI: 联合视图

    UI->>API: POST /purchase-orders 组单草稿
    Note over UI,API: 🔒 单价 · 采购员 · 采购方 · 仓库 · 供应商<br/>全是领星必填，缺一个接口就吃 500
    API->>RULE: 校验必填 + 一单一供应商
    RULE-->>API: ok / 缺哪几项
    API->>PG: BEGIN
    API->>PG: INSERT 采购单草稿 + 明细
    API->>PG: INSERT 承重墙①映射（明细 ↔ 记录 带数量）
    API->>PG: 重算各记录「已确认量」
    Note over API,PG: ★ 已确认量 = 总量 才转「已确认」<br/>否则停在原态，界面显示 200/300
    API->>PG: COMMIT
    API-->>UI: po_id

    UI->>API: POST /purchase-orders/{id}/place 下单
    API->>PG: SELECT FOR UPDATE 锁草稿
    API->>GW: create_purchase_order(payload, idem=custom_order_sn)
    GW->>LX: ⛔📤 POST /erp/sc/routing/purchase/purchase/createPurchaseOrder
    GW->>PG: INSERT erp_call（请求指纹 · 耗时）

    alt 成功
        LX-->>GW: code=0 + order_sn
        GW->>PG: UPDATE erp_call（响应）
        GW-->>API: order_sn
        API->>PG: 冻结采购单 + 记 order_sn
        API->>PG: 已下单量 = 总量 的记录 → ordered
        API-->>UI: order_sn
    else 连不上（TypeError fetch failed）
        LX--xGW: e.cause.code = ECONNRESET 等
        GW->>PG: UPDATE erp_call（cause code）
        GW-->>API: RETRIABLE
        API-->>UI: 可安全重试 —— 请求没到达领星
    else 真超时（TimeoutError）
        LX--xGW: aborted due to timeout
        GW->>LX: 📥 PurchaseOrderList 按 custom_order_sn 查重
        alt 查到了
            GW-->>API: 已建成，拿回 order_sn
        else 没查到
            GW-->>API: 确认未建，可重试
        end
    else 业务拒绝
        LX-->>GW: code != 0
        GW-->>API: REJECTED + message
        API-->>UI: 原样回显，不重试
    end
```

**读这张图要看什么**

★ **「连不上」与「真超时」必须分开处置，而且它们签名互斥：**

```
真超时  → TimeoutError: The operation was aborted due to timeout   → 必须先查重
连不上  → TypeError: fetch failed，真凶在 e.cause.code            → 可安全重试
```

只看 `e.message` 会把后者误读成前者，进而去调大超时 —— **那是一行都不会生效的改动**。
而反过来把真超时当连不上直接重试，就是**重复下单**。

```mermaid
sequenceDiagram
    autonumber
    participant UI as 前端
    participant API as API
    participant RULE as 规则层
    participant FCST as 预测函数
    participant PG as PostgreSQL
    participant CH as ClickHouse

    UI->>API: GET /plan-lines/dispatch-candidates
    API->>PG: 取 ordered / ready 的记录
    API->>RULE: 按 店铺 × 货号 跨计划累加剩余周期需求
    RULE-->>API: 候选组
    API-->>UI: 候选列表

    UI->>API: POST /sheets 建空草稿
    UI->>API: POST /sheets/{id}/lines 选择添加
    API->>CH: 在库（★ 只读 product_valid_num）· 在途
    CH-->>API: 供给
    API->>PG: 已排未发（我们自己的账）
    API->>FCST: 需求（剩余周期）
    FCST-->>API: 需求量
    API->>RULE: X = 需求 − 在库 − 在途 − 已排未发
    RULE-->>API: 逐行建议量
    API->>PG: 重建整表 + 承重墙②映射 + 记账本水位
    API-->>UI: 表 + 每行需求构成

    UI->>API: PUT 排货网格安排发货（本地仓 + 数量）
    Note over UI,API: ★ 排货单由安排派生（N-3），人不挂单
    UI->>API: PUT FBA 行 · 人工填装箱
    Note over UI,API: ★ 不填货件 —— confirmPlacementOption 之后才有
    Note over UI,API: 🔒 箱数 · 长宽高 · 单箱重量 · 单箱数量<br/>且 box_skus 要与 list 一致

    UI->>API: POST /sheets/{id}/confirm
    API->>PG: BEGIN
    API->>RULE: 确认闸 G1~G6
    alt 任一不过
        RULE-->>API: 哪一项 + 明细
        API->>PG: ROLLBACK
        API-->>UI: 409 packing_incomplete / ★ dest_incomplete /<br/>insufficient_available / ledger_moved /<br/>unlinked_shipments_pending / invalid_destination
    else 全过
        API->>PG: 整表 confirmed + 排货单 我方进度 = 已确认
        API->>PG: COMMIT（★ 触发器此后连 INSERT 一起挡）
        API-->>UI: 可投送
    end
```

**读这张图要看什么**

★ **确认闸跑在事务里，不过就 ROLLBACK。**
G3/G4/G5 三条都是「多扣一次 / 少扣一次」型错误 —— **结果看起来完全正常，只有对账才发现**。
所以必须在闸上拦死，不能靠事后发现。

## 5. 投送 · FBA（含 STA 硬闸）

```mermaid
sequenceDiagram
    autonumber
    participant UI as 前端
    participant API as API
    participant GW as ERP 网关
    participant LX as 领星
    participant AMZ as 亚马逊 SP-API
    participant PG as PostgreSQL

    API->>GW: create(consignment)
    GW->>LX: 📤 createShipmentPlan（/erp/ 本地，可逆）
    LX-->>GW: plan_sn（RP）
    GW->>PG: INSERT ext_ref

    API->>GW: lock(consignment)
    GW->>LX: 📤 FbaPlanStorageAllocate
    Note over GW,LX: ★ 可逆 —— 有 FbaPlanStorageRelease

    API->>UI: 🔒 二次确认「即将产生真实亚马逊货件」
    UI-->>API: 确认

    API->>GW: obtain_placement(consignment, idem_key)
    GW->>LX: 📥 ShipmentPlanLists 调用前查重
    alt 已存在货件

    else 未存在

        GW->>AMZ: 📤 setPackingInformation（人工填的装箱数据）
        GW->>AMZ: 📤 generatePlacementOptions
        GW->>AMZ: ⛔📤 confirmPlacementOption
        Note over GW,AMZ: ⛔ 此处产生真实亚马逊货件<br/>★ 无客户侧幂等键<br/>★ 任何失败一律转人工，绝不自动重试
        AMZ-->>GW: taskId
        GW->>AMZ: 📥 Operate 轮询 taskId
        AMZ-->>GW: shipment_id（FBA…）
        GW->>PG: INSERT ext_ref
    end

    API->>GW: create_send_order(consignment)
    GW->>LX: 📤 createReadySendOrder
    Note over GW,LX: 🔒 shipment_id 必填<br/>🔒 box_list / box_skus 必填且与 list 一致
    LX-->>GW: order_sn（SP…）
    GW->>PG: INSERT ext_ref

    API->>GW: ship(consignment)
    GW->>LX: ⛔📤 sendGoods（扣库存）
    API->>PG: 我方进度 = 已投送
    API->>PG: 计划单记录 → 已排货
```

**读这张图要看什么**

| 看点 | 为什么 |
|---|---|
| 第 5 步的**二次确认在 API 之上**，不是网关内部 | 网关不该知道「人要不要点确认」 |
| 第 8 步**调用前查重**是 FBA 唯一的幂等手段 | STA 一族没有客户侧幂等键 |
| `confirmPlacementOption` 后**必须轮询 `taskId`** | 它异步返回，不轮询就不知道货件号 |
| 装箱数据从 §3 的人工填写**一路带到 `setPackingInformation` 和 `createReadySendOrder` 两处** | 两处都必填，且要一致 |

★ **副作用必须在网关里按 path 前缀硬编码**，**按接口名判断会错** ——
`CreateShipmentPlan`（`/erp/`）与 `CreateSTATask`（`/amzStaServer/`）名字长得一样像。

★★ **前缀有三类，不是两类**（`17` 实测，2026-09-22 修）：

| 前缀 | 打到哪 | 可逆 |
|---|---|---|
| `/amzStaServer/` | ★ 亚马逊 | ⛔ **不可逆** |
| `/erp/` | 领星本地 | 可逆 |
| ★ `/basicOpen/` | 领星本地，★ **里面有写接口** | 可逆，但**是写** |

★ 实测的写接口：`/basicOpen/purchase/setOrderFinish`（整单结束到货）·
`/basicOpen/inboundOrder/inbound/setInbound`（待入库 → 已完成）·
`/basicOpen/selfShipmentOrder/deliveryGoods`（★ **标记出库、扣库存**）。

⚠️ **只认两类前缀的网关会把 `/basicOpen/` 判成「未知」** ——
而未知路径要么被放过（写进去了没人知道），要么被拦死（功能不通）。两种都错。

## 6. 每日回执对账

```mermaid
sequenceDiagram
    autonumber
    participant JOB as 回执器
    participant CH as ClickHouse
    participant PG as PostgreSQL
    participant ALERT as 告警

    JOB->>CH: 📥 按 _captured_date 取最新一版单据
    Note over JOB,CH: ★ 先去重，再比对相邻两日的行数与 SKU 覆盖数<br/>掉档超阈值 → 这批数据不可用，不是读成 0
    CH-->>JOB: 领星单据快照
    JOB->>PG: 按 ext_ref 的单号对齐
    JOB->>PG: 写「领星进度」

    alt 我方进度 = 已投送 而 领星进度 停在 待配货
        JOB->>ALERT: allocate 疑似静默失败
    end
    alt 我方进度 = 已投送 而查不到任何 ext_ref
        JOB->>ALERT: 投送在建单前就断了
    end
    alt 领星进度 = 已撤销 而我们没撤过
        JOB->>ALERT: 有人在领星里直接撤了
    end
    alt 有 ext_ref 而没有对应 erp_call
        JOB->>ALERT: ★ 架构守卫 —— 有人绕过网关直接调了领星
    end

    JOB->>PG: 领星进度 = 已完成 → 我方进度 = 已归档
    JOB->>PG: reevaluate_plan_lines（唯一实现，与触发器共用）
    JOB->>CH: 📥 采购单收货 / 入库单 → 到货量 + 到货库位
    JOB->>PG: 写到采购单上（★ 不摊回计划单记录）
    JOB->>PG: 关联采购单中有任一已到货 → 记录转「准备排货」
    Note over JOB,PG: ★ 布尔判据，不是数量判据<br/>到货量不摊分 —— 排货本来就是人做的工作
```

★ **第 2 步那条注释是整个回执器最容易被跳过、也最贵的一条。**
库存与单据日报实测会**整天缺、会掉档、会有重复行**（某日 2,217 行 / 780 SKU，
较前一日少约 40%）。**掉档那版里有货的仓会直接不出现，看起来像出库了。**
把缺失读成 0，对账就会凭空冒出一堆假差额。

## 7. 横切：一次出站写的完整时序

> ★ 这张图是**每一次** 📤 都要走的，上面各图里的 `GW->>LX` 都是它的缩写。

```mermaid
sequenceDiagram
    autonumber
    participant CALLER as 业务层
    participant GW as ERP 网关
    participant PG as PostgreSQL
    participant LX as 领星

    CALLER->>GW: call(op, payload, idem_key)
    GW->>PG: INSERT erp_call(状态=in_flight, 请求指纹)
    GW->>GW: 取 access_token（缓存）+ AES-128-ECB 签名
    GW->>LX: POST（限流分桶 + 免代理 PoolManager）

    alt code = 0
        LX-->>GW: data
        GW->>PG: UPDATE erp_call(ok, 耗时, 响应)
        GW-->>CALLER: 结果
    else 业务拒绝 code != 0
        LX-->>GW: message
        GW->>PG: UPDATE erp_call(rejected, message)
        GW-->>CALLER: REJECTED（不重试）
    else 连不上 TypeError fetch failed
        LX--xGW: e.cause.code
        GW->>PG: UPDATE erp_call(conn_failed, cause code, 打的哪个 host)
        GW-->>CALLER: RETRIABLE
    else 真超时 TimeoutError
        LX--xGW: aborted due to timeout
        GW->>PG: UPDATE erp_call(timeout)
        alt 有客户侧幂等键
            GW->>LX: 📥 回查（listOrderNos / PurchaseOrderList / ShipmentPlanLists）
            GW-->>CALLER: 已建成 或 确认未建
        else 无幂等键（STA 一族）
            GW-->>CALLER: ★ MANUAL —— 转人工，绝不自动重试
        end
    end
```

**`erp_call` 一行必须能回答三问**：

| 问 | 字段 |
|---|---|
| **打的谁** | host + path |
| **多久** | 耗时 |
| **怎么 failed 的** | `code` / `message`，或 `e.cause.code` + 打的哪个 `IP:port` |

★ **重试「成功」的那次抖动同样要留痕** —— 否则重试成功后没有任何地方记得它抖过，
下次再抖也查不出规律。

★ **回退分支必须有声。** `try/catch` 里不留日志的回退，会让「代理挂了」和「接口本身就错」
长得一模一样 —— 这是最坏的一种。

### D2 裁定：回执器怎么跑

| 项 | 裁定 | 理由 |
|---|---|---|
| 频率 | **每日一次**，cron，在 CH 采集窗口之后 | CH 延迟 ≥ 1 天，跑更密没有新数据 |
| 触发 | cron；另留一个**仅运维可用**的手动触发 | 出问题时要能立刻重跑 |
| 读哪一版 | ★ **取 `max(_captured_date)` 的最新一版，不做认知时间回放** | 单据状态表是**覆盖型**的 —— `_captured_date <= X` 在覆盖型表上滤掉的恰恰是最新数据 |
| `observed_on` | 该批 CH 数据的 `_captured_date` | 观察的是「那一天采到的样子」 |
| 第一步 | ★ **先跑采集面校验**（UC-S4），掉档超阈值 → 整批不可用、不写 | 把缺失读成倒退比读成 0 更糟 |
| 失败粒度 | 按 `ext_ref` 分批，**一批失败不影响其它批** | — |
